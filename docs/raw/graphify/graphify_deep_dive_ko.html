Executive summary

핵심 요약

먼저 “써볼 가치가 있는가?”에 바로 답하고, 뒤에서 근거를 상세히 설명한다. 아래 평가는 프로젝트 홍보 문구, 구현 코드, 공개 이슈, 직접 실험을 서로 분리해 판단한 것이다.

독립 검증 효과 있음

로컬 AST 인덱싱 속도, 파일·심볼·타입·import·주석 rationale의 구조화, 정확한 심볼에서 시작하는 주변 탐색.

조건부 효과 질문에 따라 다름

자연어 질의, 커뮤니티 지도, 영향 범위 추정, 토큰 절감. 이름이 구체적일수록 좋고 일반어일수록 잡음이 커진다.

독립 검증 대체 불가

객체 메서드·동적 디스패치의 완전한 호출 그래프, 보안 데이터 흐름, 실제 요청 실행 순서, 컴파일러 수준의 참조 정확도.

질문판정핵심 근거
무엇을 하는 프로젝트인가?프로젝트를 노드·엣지 그래프로 변환하는 로컬 우선 코드 지식 그래프 도구코드는 tree-sitter AST로 파싱하고, 결과를 graph.json, graph.html, 보고서로 내보낸다. 문서·미디어는 별도 의미 추출 단계를 사용할 수 있다.[S1][S2]
LLM이 코드를 “이해”해 그래프를 만드는가?코드 경로는 주로 아니다코드 구조는 tree-sitter 규칙 기반 추출이다. 문서·이미지·영상 등은 설정한 모델을 사용할 수 있다. 즉 코드 인덱스와 의미 추출 경로를 구분해야 한다.
실제로 빠른가?중소 규모 정적 인덱싱은 실용적우리 환경에서 9개 Python 파일은 0.30초, Graphify 패키지 80개 Python 파일·약 4.75만 LOC는 6.69초였다. 절대 시간은 하드웨어·언어·옵션에 따라 달라진다.
호출 관계를 정확히 찾는가?부분적생성자 호출은 잡았지만 service.place_order(), self.gateway.charge(), getattr 호출을 놓쳤다. 정적 해석 난도가 높은 전형적인 사례다.
자연어 검색이 좋은가?구체적 식별자에는 좋고, 넓은 질문에는 흔들림질의는 임베딩 기반 의미 이해가 아니라 문자열 점수·IDF·trigram 후보화 후 BFS/DFS 확장을 중심으로 한다.[S3]
공식 벤치마크를 믿어도 되는가?신호로는 유용하지만 확정적 증거는 아님좋은 수치를 공개했지만 메모리 벤치마크 핵심 harness와 adapter는 공개 저장소에 없다고 maintainer가 밝혔다. 코드 벤치마크는 질문 수가 6개다.[S7][S8]
추천하는가?파일럿 도입 추천, 맹신은 비추천온보딩·아키텍처 탐색·AI 문맥 축소에는 유망하다. LSP/SCIP, lexical search, CodeQL, runtime tracing과 결합해야 안정적이다.
가장 중요한 해석 규칙 Graphify가 보여 주는 “연결”은 대개 구조적 연관성이다. 연결되어 있다는 사실만으로 “A가 실행되면 B가 반드시 호출된다”, “데이터가 A에서 B로 흐른다”, “이 경로가 실제 요청 경로다”라고 결론 내리면 안 된다.

Mental model

주니어를 위한 60초 설명

Graphify를 가장 정확하게 이해하는 비유는 “코드 도시의 지도 제작기”다.

지도에서 무엇이 노드인가?

파일, 클래스, 함수, 메서드, 타입, 문서 개념, 주석의 설계 이유 등이 “장소”가 된다.

OrderService, place_order(), payments.py 같은 항목이 각각 노드다.

무엇이 엣지인가?

imports, contains, calls, inherits, references 같은 관계가 “도로”가 된다.

엣지에는 EXTRACTED, INFERRED 같은 출처 성격이 붙는다.

왜 구분해야 하나?

지도는 도로의 존재를 보여 주지만, GPS 트레이스는 실제 이동을 보여 준다. Graphify는 주로 전자다.

EXTRACTED를 “100% 사실”로 읽지 말 것 이는 보통 “소스 문법에서 직접 읽은 관계”라는 뜻이지, 전체 프로그램 의미가 완전하게 해석됐다는 뜻이 아니다. 예를 들어 self.gateway.charge()라는 구문 자체는 분명히 존재해도, 수신 객체의 정확한 타입과 대상 메서드를 해석하지 못하면 최종 호출 엣지는 빠질 수 있다.

Architecture

내부 원리와 파이프라인

공식 아키텍처는 detect → extract → build_graph → cluster → analyze → report → export 단계로 설명된다. 단계 간에는 Python dict와 NetworkX 그래프가 전달된다.[S2]

1. 파일 탐지

디렉터리를 순회해 지원 확장자를 수집하고 ignore 규칙, 파일 크기, 생성물 디렉터리 등을 필터링한다. 심볼 정확도는 이 단계에서 어떤 파일이 포함·제외되는지부터 영향을 받는다. 생성 코드, vendored 코드, monorepo 경계가 잘못 설정되면 이후 그래프도 왜곡된다.

2. tree-sitter AST 추출

tree-sitter는 소스 코드를 구체 구문 트리로 만드는 증분 파서 생성기다. 오류가 있는 파일도 비교적 견고하게 구문 구조를 만들 수 있어 에디터와 코드 도구에 많이 쓰인다.[S17] Graphify는 여러 언어 grammar를 의존성으로 포함하고, 함수·클래스·import·상속·일부 호출·타입 참조 등을 언어별 extractor로 변환한다.[S15]

이 접근의 강점 LLM 출력처럼 매번 표현이 달라지지 않고, 코드 인덱스 구축에 API 토큰이 들지 않으며, 구문 위치를 원본 줄 번호와 연결하기 쉽다.

3. 문서·미디어 의미 추출

코드 외 문서, PDF, 이미지, 영상은 별도의 의미 pass에서 AI assistant 또는 API backend를 사용할 수 있다. 이 경로는 코드 AST 경로와 달리 모델 비용·데이터 반출·프롬프트 인젝션·재현성 문제가 생긴다. 따라서 “Graphify는 완전히 로컬”이라는 표현은 코드 전용 모드에 한정해 해석하는 것이 안전하다.[S1][S14]

4. 그래프 구축

노드에는 id, label, source_file, source_location 등이 들어가고 엣지에는 관계 종류와 confidence가 붙는다. 구현상 기본 build_from_json(..., directed=False)는 NetworkX의 단순 무방향 Graph를 만든다.[S5]

EXTRACTED

import, 직접 구문, 선언처럼 소스에서 명시적으로 읽은 관계.

INFERRED

두 번째 해석 pass, 이름 해소, 공존 관계 등에서 추론한 관계.

AMBIGUOUS

대상이 불확실해 사람 검토가 필요한 관계.

confidence는 확률 점수가 아니라 관계가 만들어진 경로의 범주다. 언어·관계별 precision/recall이 보정된 값이 아니므로 EXTRACTED=1.0, INFERRED=0.7처럼 해석해서는 안 된다.

5. 커뮤니티 탐지와 허브 분석

선택적 graspologic이 있으면 Leiden, 없으면 NetworkX Louvain을 사용한다. 구현은 노드·엣지를 정렬하고 seed 42를 넣어 재현성을 높이며, 큰 커뮤니티와 결속도가 낮은 커뮤니티를 다시 분할한다. 방향 그래프도 클러스터링할 때는 무방향으로 바꾼다.[S4]

이 단계가 만드는 “서브시스템”은 코드 작성자가 선언한 모듈 경계가 아니라 그래프 연결 밀도에 따른 통계적 군집이다. 따라서 이름이 그럴듯해도 실제 bounded context나 배포 단위와 일치하는지 확인해야 한다.

6. 분석·보고·내보내기

degree가 높은 허브, 커뮤니티, 교차 연결, rationale, 질문 후보 등을 정리해 보고서와 시각화를 만든다. 여기서 가장 큰 실용적 가치는 “정답 자동 생성”보다 어디부터 읽을지 우선순위를 주는 것이다.

Retrieval internals

질의·경로 검색의 실제 원리

README의 “자연어 질문”이라는 표현만 보면 임베딩이나 LLM 의미 검색을 떠올리기 쉽다. 그러나 기본 코드 질의의 핵심은 문자열 기반 seed 선택 + 그래프 이웃 확장이다.

graphify query의 단계

  1. 토큰화: 질문을 단어로 나누고 how, what, the, work 같은 불용어를 제거한다.
  2. 후보 생성: node label, node id, source path를 합친 문자열에 대해 trigram 인덱스로 후보를 좁힌다.
  3. 점수화: exact match 1000, prefix 100, substring 1, source path match 0.5의 기본 보너스와 IDF를 결합한다.
  4. seed 선택: 상위 점수와 용어별 후보를 시작점으로 고른다. 일반 심볼이 정확히 일치하면 의도와 무관한 seed가 끼어들 수 있다.
  5. 탐색: CLI 질의는 기본적으로 depth 2의 BFS/DFS를 수행한다. 지나치게 큰 허브는 중간 경유 확장을 제한한다.
  6. 문맥 자르기: 노드와 엣지를 텍스트로 렌더링하고 대략적 token budget에서 잘라 AI에게 전달한다.

코드 확인 위 동작은 serve.py와 cli.py에서 직접 확인할 수 있다.[S3][S6]

“자연어 질의”와 “의미 검색”은 같은 말이 아니다 질문 문장을 입력할 수 있다는 사실은 맞지만, 기본 seed 선택은 문장 의미를 모델이 해석하는 방식이 아니다. GET, Path, Graph, update처럼 흔한 이름이 많은 저장소에서는 질문의 일반 단어가 결과를 크게 오염시킬 수 있다. 공개 이슈에도 Next.js의 여러 GET() 핸들러가 동시에 seed가 되어 252개 노드 중 약 90%가 무관했다는 재현 사례가 있다.[S9]

graphify path A B가 의미하는 것

path 명령은 A와 B를 같은 문자열 점수 방식으로 노드에 매핑한 뒤, 구현상 G.to_undirected()에 대해 shortest path를 찾는다. 출력에는 저장된 엣지 방향 화살표가 보이지만, 경로 선택 자체는 방향을 무시한다.[S6]

“이 두 개념 사이에 어떤 구조적 연결 고리가 존재하는가?”

단순 무방향 그래프의 구조적 한계

기본 결과가 directed: false, multigraph: false인 것은 사용성을 단순화하지만 의미 손실 위험이 있다. 방향은 호출·import·상속에서 중요하고, 동일한 노드 쌍 사이에 imports와 references 등 여러 관계가 동시에 존재할 수도 있다. 단순 Graph는 병렬 엣지를 원천적으로 표현하지 못하므로, upstream deduplication과 별개로 데이터 모델 자체는 정밀 코드 그래프보다 거칠다.

실험 D — 구버전 절대 ID 이슈의 현재성

공개 이슈 #1789는 0.8.19에서 .NET project/file node ID에 로컬 절대 경로가 들어간다고 보고한다.[S12] 우리는 0.9.12에서 두 개의 .csproj와 C# 파일을 일반 출력 위치로 분석했고 ID와 source_file 모두 상대 경로여서 해당 재현은 실패했다. 따라서 이 이슈를 현재 버전의 확정 취약점으로 단정하지 않고, 위의 별도 --out 사례와 구분한다.

결론을 제한하는 부분

핵심 memory harness 비공개

공개 이슈에서 maintainer는 memory/runner.py와 adapter가 public repo에 없고, 별도의 live research harness로 유지 중이라고 답했다. 따라서 공개 저장소만으로 headline 결과를 독립 재현할 수 없다.[S8]

코드 평가 n=6

ERPNext가 큰 저장소라는 점은 좋지만 질문 6개는 일반화에 매우 작다. 질문 선정·gold fact 작성·agent prompt가 결과에 큰 영향을 미칠 수 있다.

자체 제작·자체 평가

도구 제작자가 harness와 설정을 함께 설계했다. 악의적이라는 뜻이 아니라, 독립 replication 전에는 “가능성을 보여 주는 연구 결과”로 보는 것이 표준적이다.

서로 다른 제품 범주 비교

대화 메모리, dense RAG, 구조 그래프는 ingest 방식과 목적이 다르다. 한 데이터셋의 우위가 코드 이해 전반의 우위를 뜻하지 않는다.

내장 graphify benchmark의 19.3×를 그대로 믿으면 안 되는 이유

우리 self-index graph에서 내장 benchmark는 평균 19.3× fewer tokens를 출력했다. 그러나 구현을 보면 corpus word 수가 없을 때 node_count × 50으로 추정하고, query context는 문자 수를 4로 나누며, 고정된 일반 질문 다섯 개를 사용한다.[ref-s19] 

Corpus estimate: nodes × 50 words
Token estimate:  characters ÷ 4
Reduction:       estimated corpus tokens ÷ estimated subgraph tokens
이 수치가 말하는 것과 말하지 않는 것 말하는 것: 그래프 subgraph가 전체 corpus 추정보다 작을 수 있다.
말하지 않는 것: 답이 정확하다, 필요한 파일이 포함됐다, 개발 시간이 19.3배 단축됐다, 비용이 실제로 19.3배 줄었다.

이번 조사에서 프로젝트 팀과 독립된 대규모 공개 replication은 찾지 못했다. 따라서 현재 가장 균형 잡힌 표현은 “성능 가능성은 보였지만, 대표적인 실제 개발 작업에서 독립 검증이 더 필요하다”다.

Trade-offs

장점과 단점

장점

  1. 코드 구축이 로컬·결정적: API 비용 없이 반복 구축 가능.
  2. 폭넓은 언어 지원: 하나의 추상 그래프로 polyglot 저장소를 훑기 좋음.
  3. 설명 가능한 출처: 파일·줄·관계 종류·confidence가 있어 vector-only 검색보다 추적이 쉬움.
  4. 구조적 탐색: 단순 텍스트 검색이 놓치는 파일 간 import/type/상속 이웃을 한 번에 볼 수 있음.
  5. AI 문맥 축소: 전체 파일을 무작정 넣지 않고 작은 subgraph로 시작 가능.
  6. 온보딩 보조: 허브와 커뮤니티가 “무엇부터 읽을지” 제시.
  7. rationale 승격: # WHY:, ADR/RFC 참조를 구조 노드로 다루는 아이디어가 실용적.
  8. 낮은 시작 장벽: JSON/HTML/Markdown 산출물과 CLI로 별도 서버 없이 시작.

단점

  1. 호출 완전성 한계: 객체 수신자 타입, DI, reflection, metaprogramming, event bus, generated code가 어렵다.
  2. 자연어 질의의 어휘 의존: 일반 심볼·동명 함수가 seed를 오염시킨다.
  3. 연결과 인과의 혼동: 무방향 path가 실행 흐름처럼 보일 수 있다.
  4. staleness 위험: 신규 파일을 check-update가 놓치는 현재 이슈가 있다.
  5. 대형 artifact 운영: 공개 이슈는 큰 모듈에서 300MB–1GB graph 폴더, branch 충돌, 공유 문제를 보고한다.[S11]
  6. 빠른 버전 변동: 릴리스 속도가 빨라 pinning과 회귀 검증이 필요.
  7. 독립 evidence 부족: headline benchmark의 public reproduction 경로가 불완전.
  8. 문서·미디어 경로는 LLM 리스크: 비용·기밀성·프롬프트 인젝션·모델 편차가 다시 들어온다.

Hidden failure modes

놓치기 쉬운 사각지대

단순 기능 목록보다 실제 도입에서 더 자주 문제가 되는 부분들이다.

1. 그래프가 정교해 보일수록 과신하기 쉽다

수천 개 노드, 색깔별 커뮤니티, 화살표가 있는 시각화는 권위 있어 보인다. 그러나 “예쁘고 복잡한 시각화”는 correctness evidence가 아니다. 누락된 호출은 화면에 나타나지 않으므로 사용자는 누락 자체를 알아차리기 어렵다.

2. 높은 degree가 중요도를 뜻하지 않을 수 있다

공통 utility, base type, index file, 설정 허브는 연결이 많지만 제품적으로 중요한 도메인 로직이 아닐 수 있다. degree 중심 “god node”는 구조적 중심성이지 비즈니스 중요도·변경 위험·운영 트래픽이 아니다.

3. 정적 그래프는 feature flag와 런타임 구성을 모른다

같은 코드를 두고 환경 변수, DI container, tenant 설정, A/B flag, plugin registry가 다른 구현을 선택할 수 있다. 정적 그래프에는 가능한 후보가 섞이거나 아예 해소되지 않으며, “현재 production에서 선택된 구현”은 trace나 설정 snapshot이 필요하다.

4. 생성 코드와 빌드 후 변환

protobuf/OpenAPI client, ORM model, macro, annotation processor, transpiler, codegen이 실제 실행 코드를 만든다면 source tree만 본 그래프는 전후 단계 중 하나만 반영한다. 생성물을 포함하면 노이즈와 중복이 늘고, 제외하면 실제 호출 대상이 빠진다.

5. 모노레포 경계와 동일 심볼 충돌

여러 서비스에 handler, index, GET, Config가 반복된다. 경로·패키지·signature를 포함한 안정적 identity가 없으면 query seed와 노드 병합 모두 오염될 수 있다. 최근 구현은 path-qualified ID와 충돌 방어를 늘렸지만, 공개 이슈가 계속 나오는 영역이다.[S5][S9]

6. graph artifact 자체가 민감 정보다

코드 원문이 없더라도 파일 구조, 내부 서비스명, 클래스명, 데이터 모델, 설계 이유, 보안 모듈 위치, 절대 경로가 들어갈 수 있다. 외부 LLM·공개 버킷·Git history에 올리기 전에는 소스 코드와 비슷한 등급으로 다뤄야 한다.

7. 설치가 assistant 행동을 바꾼다

graphify install과 플랫폼별 install은 AGENTS.md, Cursor rules, hooks, settings 등에 “검색 전 그래프를 우선 사용하라”는 지속 지시를 쓸 수 있다.[S1] 그래프가 stale하거나 query가 부정확한데도 agent가 원본 검색을 회피하면 품질이 오히려 내려갈 수 있다. 초기 파일럿에서는 always-on hook을 설치하지 말고 수동 비교하는 편이 안전하다.

8. 프롬프트 인젝션 방어는 완전하지 않다

프로젝트는 URL SSRF, XSS, path traversal, node label sanitization, 문서 의미 추출 시 untrusted delimiter와 알려진 sentinel neutralization 등을 구현한다. 이는 좋은 방어다.[S14] 동시에 보안 문서도 “injection을 불가능하게 만들지는 않는다”고 인정한다. 공격자가 통제하는 문서·README·issue dump를 의미 추출할 때는 별도 trust boundary가 필요하다.

9. 공급망과 재현 가능한 설치

공식 이름이 흔한 graphify가 아니라 graphifyy이고, optional extra가 많아 잘못된 패키지나 불필요한 의존성을 설치하기 쉽다. 검토 시 PyPI 0.9.12 파일은 Trusted Publishing이 아니라 twine으로 업로드돼 있었다.[S16] 이것이 침해 증거는 아니지만, 조직 환경에서는 버전·hash 고정, SBOM, dependency audit를 적용할 이유가 된다.

10. 갱신 실패는 조용할수록 위험하다

신규 파일이 생겼는데 check-update가 성공 코드와 무출력으로 끝나는 문제는 “실패”보다 위험할 수 있다. 사용자는 최신이라고 믿고 stale graph를 agent에게 우선시킨다. freshness를 graph 생성 commit SHA, corpus manifest keyset diff, added/changed/deleted count로 명시해야 한다.

11. 그래프 크기와 Git의 궁합

큰 JSON/HTML을 Git에 커밋하면 diff가 불친절하고, branch마다 같은 artifact가 충돌하며, history가 팽창한다. 중앙 store·object storage·LFS 제안이 공개 이슈에 있지만, 그 자체도 access control·cache invalidation·branch/version key 설계를 요구한다.[S11]

12. 비용 절감이 작업 성공률 저하로 상쇄될 수 있다

작은 문맥은 싸지만 필요한 증거가 빠지면 agent가 틀린 답을 더 싸게 만들 뿐이다. 최적화 목표는 “토큰 최소화”가 아니라 정답당 비용(cost per correct task)이어야 한다.

개선 포인트 1 — 관계별 모드를 분리

하나의 path로 모든 질문을 처리하지 말고 concept_path, call_path, data_flow, runtime_trace를 분리해야 한다. 각 모드는 허용하는 엣지 종류·방향·confidence threshold가 달라야 한다.

개선 포인트 2 — directed typed multigraph

핵심 저장 형식은 방향과 병렬 관계를 보존하는 multigraph가 적합하다. A imports B, A calls B, A references B를 하나의 관계로 덮어쓰지 않고 각각의 provenance와 source span을 유지해야 한다.

개선 포인트 3 — exact resolver 우선, fuzzy query는 후보 생성용

자연어가 구체 심볼로 해석될 때는 LSP/SCIP의 fully-qualified symbol과 signature를 우선한다. fuzzy lexical/semantic 검색은 top-k 후보만 만들고, path·module·community·caller context로 재순위화한다. 동명 label 수가 많을수록 multiplicity penalty를 줘야 한다.

개선 포인트 4 — source snippet을 최종 evidence로

그래프 텍스트만 AI에 주지 말고, 상위 노드·엣지를 만든 원본 코드 주변 10–30줄을 함께 제공해야 한다. 답변은 “그래프 관계”와 “원본 코드 인용”을 구분하고, 둘이 충돌하면 원본을 우선해야 한다.

개선 포인트 5 — freshness를 first-class metadata로

  • 그래프 생성 시점의 Git commit SHA와 dirty state 저장
  • 각 source의 content hash, extractor version, parser version 기록
  • manifest keyset으로 added/changed/deleted를 모두 비교
  • 질의 결과에 stale 여부와 마지막 검증 시각 표시
  • branch·worktree별 artifact namespace 분리

개선 포인트 6 — relation별 품질 측정

전체 노드 수나 token reduction 대신 언어별·관계별 precision/recall을 측정해야 한다. 예: Python direct_call, TypeScript import, Java inherits, C# project reference. confidence label도 이 통계를 바탕으로 보정하면 실제 의미가 생긴다.

Adoption playbook

안전한 도입 방법

가장 좋은 도입은 “전사 설치”가 아니라 한 저장소의 작은 비교 실험이다.

1단계 — 버전과 범위 고정

특정 릴리스를 pin하고 한 언어·한 서비스부터 시작한다. 문서·미디어 backend와 always-on hook은 처음에는 끈다.

2단계 — 실제 질문 세트 작성

온보딩, 정의/참조, 호출, 영향 범위, 보안, 운영 흐름에서 30–50개 질문을 고르고 gold file/function/evidence를 만든다.

3단계 — baseline 비교

기존 rg + IDE/LSP + agent와 Graphify 추가 조건을 같은 모델·budget·시간 제한으로 비교한다.

4단계 — 오류 유형 분석

누락 호출, 잘못된 동명 심볼, stale artifact, false causal path, 절대 경로·민감 label을 분류한다.

5단계 — 제한적 통합

효과가 확인된 질문 유형에만 graph-first를 켜고, 실패 유형은 LSP/검색/CodeQL/trace로 routing한다.

6단계 — 지속 회귀 평가

Graphify·parser·저장소 버전이 바뀔 때 gold 질문을 재실행한다.

예시 합격 기준

  • 기존 baseline보다 top-5 source recall이 최소 10%p 향상된다.
  • 전체 task success가 향상되고, 비용 절감 때문에 정확도가 떨어지지 않는다.
  • 정확한 call 질문의 false causal path가 조직 허용치 이하이다.
  • 추가·변경·삭제 파일 freshness test가 100% 통과한다.
  • artifact에 절대 사용자 경로·secret·규제 데이터가 없다.
  • 버전 upgrade 후 gold 질문 회귀가 자동 실행된다.

보수적인 시작 명령

# 1) 공식 패키지 이름과 버전을 명시
uv tool install "graphifyy==0.9.12"
graphify --version

# 2) 첫 파일럿은 코드만. LLM 의미 추출과 always-on hook은 보류
graphify extract . --code-only

# 3) 일반어보다 fully-qualified symbol / 파일 경로를 포함
graphify query "src/shop/services/orders.py OrderService place_order" --context call

# 4) path는 구조적 연결 후보로만 사용
# 실제 호출 여부는 LSP references, 원본 코드, 테스트로 확인
graphify path "OrderService.place_order" "Database.save_order"

# 5) 커밋 전 artifact 검사
rg -n '(/Users/|/home/|[A-Z]:\\\\Users\\\\|AKIA|BEGIN .*PRIVATE KEY)' graphify-out
초기에는 graphify install을 나중에 먼저 CLI를 수동으로 사용해 baseline 대비 이득을 확인하라. always-on assistant rule과 Git hook을 먼저 설치하면 Graphify를 우선 사용하도록 행동이 바뀌어 공정한 비교가 어려워진다.

누가 쓰면 좋은가

적합

  • 수만~수백만 LOC의 polyglot monorepo
  • 신규 개발자 온보딩 비용이 큰 팀
  • AI coding agent가 반복적으로 저장소를 탐색하는 환경
  • 코드·ADR·스키마·인프라 개념을 한 지도에서 보고 싶은 팀
  • 정답 도구가 아니라 탐색 보조 도구로 운영할 성숙도가 있는 팀

단독 사용 부적합

  • 보안 감사를 Graphify만으로 수행하려는 경우
  • 실제 런타임 호출 순서·latency·branch가 필요한 경우
  • reflection·macro·DI·plugin이 매우 많은 동적 시스템
  • 작아서 IDE와 rg만으로 충분한 저장소
  • artifact를 통제 없이 public Git·외부 AI에 공유하는 환경

Final assessment

최종 판단

Graphify의 핵심 아이디어는 타당하다. LLM이 매번 저장소 전체를 다시 읽게 하는 대신, 결정적 AST 추출로 재사용 가능한 구조 인덱스를 만들고 관련 subgraph만 전달하는 방식은 비용·속도·설명 가능성 측면에서 매력적이다. 작은 fixture와 약 4.75만 LOC 패키지 실험에서도 구축은 실제로 빠르고, 파일·심볼·타입·주석의 구조 지도로서 유용했다.

동시에 현재 구현은 “지식 그래프”라는 이름이 줄 수 있는 기대보다 거칠다. 기본 질의는 lexical scoring과 깊이 2 그래프 탐색에 크게 의존하고, 기본 그래프는 단순 무방향이며, path는 방향을 무시한 shortest path다. 객체 메서드와 동적 호출을 놓친 실험, 동명 GET()의 질의 오염, 신규 파일 freshness 실패는 이 한계를 구체적으로 보여 준다.

공식 벤치마크는 가능성을 보여 주지만, memory harness가 공개되지 않았고 코드 질문 수가 6개라 독립 검증 전에는 결정적 근거로 보기 어렵다. 스타 수와 빠른 릴리스도 채택 신호일 뿐 정확도 증거가 아니다.

권고

파일럿은 해볼 가치가 있다. 단, Graphify를 “권위 있는 프로그램 분석기”가 아니라 “범용 구조 지도 + AI 검색 가속기”로 정의하라. 정확한 심볼은 LSP/SCIP, 보안 흐름은 CodeQL, 실제 실행은 OpenTelemetry, 텍스트 증거는 rg/Zoekt로 확정하고, Graphify가 그 사이를 연결하게 하라.

  • 공개 저장소 README, architecture, benchmark, security, packaging 설정과 핵심 query/build/cluster/benchmark 코드.
  • 최근 공개 이슈 중 query ambiguity, freshness, artifact sharing, path privacy, deletion handling.
  • PyPI graphifyy 0.9.12의 Python·C# 코드 AST 추출, clustering, query, path, update, check-update.
  • 작은 합성 Python fixture와 설치된 Graphify Python 패키지 자체.

검증하지 못한 범위

  • 약 40개 언어 각각의 extractor precision/recall.
  • 문서/PDF/이미지/영상의 LLM 의미 추출 품질과 비용.
  • Neo4j/FalkorDB, MCP HTTP, 모든 assistant integration과 hook.
  • Windows/macOS, 대규모 monorepo, 1M+ LOC에서의 독립 성능.
  • 비공개 memory benchmark harness의 재실행.
  • 보안 침투 테스트와 전체 dependency vulnerability audit.

재현성 주의

시간·메모리는 컨테이너의 cold/warm cache, 가상 CPU, Python 버전, 설치 extras, 파일 시스템의 영향을 받는다. 따라서 절대 수치보다 “기능 동작 여부와 실패 패턴”을 중심으로 해석해야 한다. 저장소 v8/0.9.13의 최신 수정 일부는 PyPI 0.9.12 실험에 포함되지 않을 수 있다.

실험용 핵심 코드

class OrderService:
    def __init__(self, db: Database, gateway: PaymentGateway):
        self.db = db
        self.gateway = gateway

    def place_order(self, user: User, total: float) -> Order:
        txn = self.gateway.charge(total)      # 호출 엣지 누락
        order = Order(id=len(txn), user_id=user.id, total=total)  # 포착
        self.db.save_order(order)             # 호출 엣지 누락
        return order

def create_order(service: OrderService, email: str, total: float):
    user = User(id=1, email=email)            # 포착
    return service.place_order(user, total)   # 호출 엣지 누락
