AWS에서 정적 프런트엔드와 서버리스 BFF를 조합하는 구조는 합리적이다. 그러나 “Next.js를 S3에 올리고 Lambda가 백엔드를 대신한다” 정도로 이해하면 중요한 경계를 놓친다. 정적 내보내기는 Next.js 서버 기능을 제거하고, BFF는 도메인 백엔드가 아니라 브라우저 전용 경계다. CloudFront 경로 순서, API 원본 우회, 쿠키 기반 CSRF, API Gateway 30초 제한, Lambda의 VPC 인터넷 경로까지 함께 설계해야 한다.

제공된 아키텍처 보고서를 AWS와 Next.js의 현재 공식 문서, 그리고 ReadMates의 실제 ADR과 대조했다. 그 결과 기본 방향은 타당했지만 CloudFront 고정 요금제, 원본 보호, 장시간 요청과 VPC 비용에는 보정이 필요했다.

## 먼저 알아야 할 개념

정적 프런트엔드는 빌드 시 HTML·JavaScript·CSS 파일을 만들고 CDN에서 전달한다. 요청마다 Node 서버가 페이지를 렌더링하지 않는다. Vite SPA는 대표적인 예이고, Next.js도 `output: 'export'`를 사용하면 정적 파일을 만들 수 있다.

BFF(Backend for Frontend)는 브라우저 바로 뒤의 얇은 서버 경계다. 쿠키 전달, 브라우저에 숨겨야 할 자격 증명 주입, 응답 모양 조정, 업스트림 호출을 담당한다. 주문 규칙이나 회원 정책, 데이터베이스 접근 같은 도메인 로직은 기존 Spring 서버가 계속 소유해야 한다.

이 글의 기준 구조는 다음과 같다.

`브라우저 → CloudFront → S3 정적 파일`

`브라우저 → CloudFront /api/* → API Gateway → Lambda BFF → 사설 Spring`

같은 도메인 아래 정적 파일과 API를 배치하면 브라우저 CORS를 단순화할 수 있다. 하지만 같은 출처라는 사실만으로 인증과 CSRF가 해결되지는 않는다.

## 실제 구조

### 프런트엔드 선택

Next.js 16의 정적 내보내기는 Server Components도 빌드 시 렌더링할 수 있지만, 요청 시점 서버 기능은 사용할 수 없다. 공식 문서가 열거한 비지원 기능에는 `generateStaticParams` 없는 동적 라우트, cookies, rewrites, redirects, headers, proxy, ISR, 기본 이미지 최적화, Draft Mode, Server Actions 등이 포함된다. Route Handler도 정적 `GET` 결과는 만들 수 있지만 요청별 동작은 불가능하다.

따라서 선택 기준은 브랜드가 아니라 런타임 요구다.

- 로그인 이후 브라우저 앱이고 SEO·요청별 서버 렌더링이 필요 없다면 Vite SPA가 단순하다.
- 파일 기반 라우팅과 빌드 시 렌더링이 필요하고 모든 경로를 미리 만들 수 있다면 Next.js 정적 내보내기도 맞는다.
- cookies, SSR, ISR, Server Actions가 필요하다면 S3 정적 배포가 아니라 Next.js 서버 런타임을 운영해야 한다.

Next.js 공식 BFF 문서도 자체 백엔드 기능을 “완전한 백엔드 대체재”로 보지 말라고 설명한다. 정적 내보내기에서는 그 제한이 더 강하다.

### CDN과 원본

S3는 웹사이트 엔드포인트가 아니라 일반 버킷 원본으로 연결하고, CloudFront Origin Access Control(OAC)로 읽기를 제한하는 것이 현재 권장 방식이다. OAC는 S3 웹사이트 엔드포인트에는 적용되지 않는다.

CloudFront 캐시 동작은 **먼저 일치한 경로가 승리**한다. `/api/*` 동적 동작을 기본 `*` 정적 동작보다 앞에 두지 않으면 API 요청이 S3로 갈 수 있다. 정적 자산에는 긴 TTL과 해시 파일명을 쓰고, API에는 캐시를 끄거나 의도한 키만 사용해야 한다. 특히 최소 TTL이 0보다 크면 원본의 `no-cache`, `no-store`, `private`보다 우선할 수 있다.

### BFF와 사설 백엔드

API Gateway HTTP API는 Lambda에 이벤트를 전달하고 Lambda는 Spring으로 요청을 프록시한다. Payload Format 2.0에서는 중복 헤더가 합쳐지고 쿠키가 별도 필드로 표현되므로 `Set-Cookie`와 다중 헤더를 명시적으로 테스트해야 한다.

Lambda를 VPC에 연결하면 사설 EC2에 접근할 수 있지만, 함수의 기본 인터넷 접근은 사라진다. 공개 API 호출이 필요하면 NAT 경로 또는 필요한 VPC 엔드포인트를 설계해야 한다. Lambda를 public subnet에 넣는 것만으로 인터넷이 생기지는 않는다.

## 핵심 기능

운영 가능한 최소 설계에는 다음 계약이 필요하다.

1. CloudFront의 `/api/*`가 정적 기본 동작보다 먼저 매칭된다.
2. S3 버킷은 공개 접근을 막고 특정 배포의 OAC만 허용한다.
3. API Gateway 기본 `execute-api` 엔드포인트를 비활성화하거나 별도 원본 인증으로 CloudFront 우회를 막는다.
4. Lambda는 허용한 경로·메서드·헤더만 전달하고 hop-by-hop·내부 헤더를 제거한다.
5. Spring은 인증·도메인 규칙·DB의 유일한 소유자이고 BFF는 상태와 DB를 갖지 않는다.
6. 쿠키 인증의 상태 변경 요청은 `Origin` 검증, SameSite 정책, 필요 시 CSRF 토큰을 사용한다.
7. 요청 ID를 CloudFront부터 Spring까지 전달하고 로그에서 토큰·쿠키·개인정보를 가린다.
8. 정적 배포는 해시 자산을 먼저 올리고 HTML을 마지막에 배포하며 이전 자산을 일정 기간 보존한다.

ReadMates의 2026년 4월 ADR도 비슷한 경계를 택한다. Vite SPA와 Pages Functions를 같은 출처로 제공하고, BFF는 쿠키 전달과 내부 비밀 주입만 담당하며 Spring이 인증·도메인·DB를 소유한다. 이것은 ReadMates에 채택된 설계의 근거이지, 모든 AWS 시스템의 정답이라는 증거는 아니다.

## 좋은 점

정적 파일은 애플리케이션 서버보다 배포와 확장이 단순하고 CDN 캐시 효율이 높다. BFF가 브라우저와 백엔드 사이에 있으면 내부 주소와 자격 증명을 브라우저에 노출하지 않고, 프런트엔드에 맞춘 쿠키와 오류 계약을 한곳에서 관리할 수 있다.

서버리스 BFF는 유휴 트래픽이 적은 서비스에서 상시 실행 서버를 추가하지 않고 요청량에 따라 확장할 수 있다. 또한 프런트엔드 배포와 Spring 도메인 서버의 수명 주기를 분리할 수 있다.

## 조심해야 할 점

가장 먼저 확인할 것은 **CloudFront 요금제와 기능의 불일치**다. 현재 고정 요금제 표에서 Free·Pro는 사용자 정의 캐싱 규칙과 사용자 정의 원본 요청 규칙을 제공하지 않고, VPC 사설 원본도 Business 이상에 표시된다. Pro가 월 15달러라는 이유만으로 `/api/*` 정책과 사설 원본 요구에 맞는다고 가정하면 안 된다. 종량제(PAYG)를 포함해 실제 필요한 기능 기준으로 다시 비교해야 한다.

비용도 요청 횟수 하나로 계산할 수 없다. CloudFront 전송·요청 또는 요금제, API Gateway 호출, Lambda 요청과 실행 시간, CloudWatch 로그, WAF, Route 53, S3, 무효화, 데이터 전송을 합쳐야 한다. Lambda가 외부 인터넷을 위해 NAT Gateway를 쓰면 낮은 트래픽에서도 고정 비용이 크게 느껴질 수 있다. 트래픽·리전·응답 크기가 없으면 정확한 월 비용을 사실로 제시할 수 없다.

기술적 사각지대도 있다.

- API Gateway HTTP API 통합 제한은 최대 30초다. 긴 AI 생성, SSE, WebSocket, 대용량 작업은 비동기 작업·이벤트 채널로 분리해야 한다.
- 요청·응답 payload 한도는 10MB다. 큰 파일은 BFF를 통과시키지 말고 presigned S3 업로드를 사용한다.
- CloudFront 사용자 정의 오류 응답으로 SPA의 `index.html`을 돌려줄 때 API의 401·404까지 200 HTML로 바꾸면 안 된다.
- Lambda 동시성이 갑자기 늘면 단일 Spring EC2를 압도할 수 있다. 예약 동시성, 타임아웃, 재시도 제한, 백프레셔가 필요하다.
- 단일 EC2는 가용성·패치·롤백의 단일 장애점이다. 백업, 헬스 체크, 무중단 교체 또는 허용 가능한 중단 시간을 명시해야 한다.
- 같은 출처 쿠키는 CORS를 줄이지만 CSRF와 세션 고정 문제를 자동으로 막지 않는다.

Lambda Function URL에 CloudFront OAC를 붙이는 대안도 있다. 하지만 공식 문서상 POST·PUT 요청은 클라이언트가 payload의 SHA-256을 계산해 헤더를 추가해야 하고 Function URL은 인터넷을 통해서만 접근하므로, 일반 브라우저 BFF의 단순한 기본값으로 보기는 어렵다.

## 언제 쓰면 좋은가

이 구조는 프런트엔드가 대부분 정적이고, 요청이 짧으며, 업스트림 API가 명확하고, 트래픽 변동이 큰 서비스에 잘 맞는다. 기존 Spring 서버를 외부에 직접 노출하지 않으면서 프런트엔드만 빠르게 배포하려는 경우에도 유용하다.

요청별 SSR, 장시간 스트리밍, 고빈도 저지연 내부 통신, 무거운 BFF 도메인 로직이 필요하면 다른 구조가 낫다. 그 경우 Next.js 서버 런타임, ALB/ECS, 비동기 큐와 작업자, 전용 API 서비스 등을 요구사항별로 비교해야 한다.

## 주니어 개발자가 배울 점

첫째, 정적 배포는 프레임워크 이름이 아니라 “요청 시 서버 기능을 쓰는가”로 판단한다.

둘째, CDN 경로 규칙은 코드만큼 중요한 보안 설정이다. 첫 일치 규칙과 기본 동작, 캐시 키를 테스트해야 한다.

셋째, private subnet은 자동 보안이나 자동 인터넷을 뜻하지 않는다. 들어오는 경로, 나가는 경로, DNS, 보안 그룹을 따로 그려야 한다.

넷째, 서버리스 비용은 “서버가 없다”가 아니라 비용 항목이 여러 서비스로 나뉜다는 뜻이다. 특히 NAT와 로그는 작은 서비스의 예상 밖 비용이 되기 쉽다.

## 내 결론

나는 이 아키텍처를 조건부로 추천한다. 정적 요구가 명확하고 BFF를 얇게 유지한다면 CloudFront·S3·API Gateway·Lambda는 책임이 잘 분리된 조합이다. 다만 먼저 Next.js의 비지원 기능을 체크하고, CloudFront 요금제가 필요한 캐시·원본 기능을 제공하는지 확인해야 한다.

첫 구현은 `/health`와 한 개의 읽기 API로 시작하겠다. CloudFront를 거친 성공, API Gateway 직접 접근 차단, 쿠키·다중 헤더, 401·404, 30초 타임아웃, VPC에서 Spring 및 외부 의존성 접근을 각각 시험한다. 그 증거가 나온 뒤에 전체 API와 트래픽 비용 모델을 확장하는 것이 안전하다.
