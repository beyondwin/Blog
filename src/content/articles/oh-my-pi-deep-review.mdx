oh-my-pi(이하 OMP)를 “기능이 많은 터미널 코딩 에이전트”라고만 부르면 절반만 맞다. 저장소를 직접 보면 이 프로젝트의 정체성은 모델보다 실행 환경에 가깝다. LSP와 디버거, 구조적 편집, 셸, 브라우저, MCP, 세션 기억, 협업, 서브에이전트를 한 작업대에 올려놓고 모델이 실제 개발 흐름을 끝까지 밀어붙이게 한다.

이번 글은 전달받은 HTML 보고서를 블로그 문법으로 옮긴 글이 아니다. 2026년 7월 12일에 `can1357/oh-my-pi`를 새로 클론해 commit `20c0a2e4101d8507e7cbbaf547baa4f9f2340b73`의 코드와 테스트, CI, 공식 문서, 릴리스, 현재 이슈 상태를 다시 확인했다. TypeScript 정적·타입 검사를 돌렸고, 독립 실행 가능한 보안·릴리스 테스트 60개도 통과시켰다. 그 과정에서 원문에 없거나 충분히 강조되지 않은 사각지대도 따로 추적했다.

결론부터 말하면 OMP는 충분히 실전적이다. 특히 복잡한 저장소에서 탐색과 수정, 검증 사이의 왕복을 줄이는 능력은 매력적이다. 다만 기본값 그대로 조직에 배포할 성격의 도구는 아니다. 자동완성 앱이 아니라 파일, 셸, 브라우저, 원격 도구 자격증명을 다루는 특권 런타임으로 봐야 한다.

| 관점 | 짧은 판단 |
| --- | --- |
| 정체성 | 모델이 아니라 여러 개발 도구와 실행 권한을 묶는 agent harness다. |
| 가장 큰 강점 | “찾기 → 이해 → 수정 → 실행 → 검증”이 한 세션에서 이어진다. |
| 가장 큰 위험 | 기본 승인 모드가 `yolo`이고, 확장·MCP·브라우저·서브에이전트가 권한을 넓힌다. |
| 개인 사용 | 전용 프로필과 좁은 권한으로 시작하면 생산성이 높다. |
| 팀 사용 | 버전 고정, 격리, 자격증명 분리, CI·리뷰 게이트가 있어야 한다. |

## 먼저 알아야 할 개념

OMP를 이해할 때는 모델, 도구, 하네스를 분리해서 보는 편이 좋다.

모델은 다음에 무엇을 할지 판단한다. 도구는 파일을 읽고 고치거나 명령을 실행하고 브라우저를 조작한다. 하네스는 그 둘 사이에서 세션을 만들고, 어떤 도구를 보여줄지 정하고, 승인 정책을 적용하고, 실패와 재시도, 컨텍스트 압축, 로그, 서브에이전트를 관리한다.

이 구분이 중요한 이유는 간단하다. 모델이 더 좋아진다고 해서 실행 경계가 자동으로 안전해지지는 않는다. 반대로 하네스가 잘 설계되면 같은 모델도 훨씬 안정적으로 저장소를 탐색하고 검증할 수 있다.

OMP에서 자주 등장하는 용어도 이 틀로 보면 어렵지 않다.

- **LSP**는 IDE가 타입, 정의, 참조, 진단을 얻는 표준 프로토콜이다.
- **DAP**는 중단점과 스택, 변수 같은 디버거 기능을 연결한다.
- **AST 또는 구조적 편집**은 코드를 단순 문자열이 아니라 문법 트리로 보고 수정한다.
- **MCP**는 GitHub, 데이터베이스, 사내 서비스 같은 외부 도구를 모델에게 연결한다.
- **RPC·ACP·SDK**는 사람이 TUI를 직접 쓰지 않고 다른 프로그램이 OMP를 구동하는 입구다.
- **서브에이전트**는 큰 작업을 조사, 구현, 검토 역할로 나눠 동시에 수행하는 별도 실행 단위다.

비유하면 모델은 두뇌이고 OMP는 IDE, 터미널, 브라우저, 작업 기록과 열쇠 꾸러미가 놓인 작업실이다. 좋은 작업실은 일을 빠르게 만든다. 하지만 열쇠가 많아질수록 “누가 어떤 지시로 무엇을 열 수 있는가”가 더 중요해진다.

## 실제 구조

저장소의 `packages/coding-agent/DEVELOPMENT.md`와 실제 `src/` 구조를 같이 보면 진입점은 여러 개지만 중심은 하나다. CLI 인자를 해석한 뒤 TUI, print, RPC, ACP 같은 모드로 갈라지고, 결국 `AgentSession`과 도구 레지스트리, 모델 레지스트리, 세션 저장소를 조합한다. SDK로 임베드할 때도 같은 핵심 런타임을 쓴다.

코드는 기능별로 꽤 잘 나뉘어 있다.

- `src/session/`은 메시지, 모델 호출, 압축, 재시도, 저장과 복원을 맡는다.
- `src/tools/`와 `src/capability/`는 실제 도구 실행과 권한 tier를 나눈다.
- `src/task/`는 서브에이전트의 병렬 실행, 예산, 수명, 격리와 결과 수집을 다룬다.
- `src/extensibility/`는 extension, hook, plugin, skill, custom tool의 진입점이다.
- `src/mcp/`는 stdio·HTTP 전송, OAuth, 도구 등록과 호출을 묶는다.
- `src/memories/`와 `src/mnemopi/`는 세션을 넘어가는 기억과 회상을 관리한다.
- `src/collab/`과 `packages/collab-web`은 암호화된 세션 공유와 게스트 제어를 구현한다.

이 분리는 단순히 폴더가 예쁘다는 의미보다 중요하다. 예를 들어 MCP 연결 실패와 세션 저장 실패, 도구 승인 실패를 서로 다른 경계에서 다룰 수 있다. 1,000개가 넘는 coding-agent 테스트 파일과 계약 중심 테스트 규칙도 프로젝트가 실제 운영 회귀를 많이 겪고 다듬어졌다는 신호다.

검증한 HEAD의 패키지 버전은 `16.4.6`이었고, GitHub API가 돌려준 최신 공개 릴리스는 `v16.4.5`였다. 하루 전 원문에 적힌 `v16.4.4`는 이미 지나가 있었다. 이 속도는 유지보수가 활발하다는 장점과, 사용자가 계속 회귀 검증을 해야 한다는 부담을 동시에 보여준다.

## 핵심 기능

OMP의 핵심은 개별 기능 수가 아니라 기능 사이의 연결이다.

낯선 저장소를 예로 들어보자. 먼저 파일 검색과 LSP로 호출 관계를 좁힌다. 필요한 부분만 읽고 구조적 편집이나 hash-anchored edit로 수정한다. 이어서 테스트를 실행하고, 실패하면 DAP나 셸 출력으로 원인을 좁힌다. 외부 문서가 필요하면 웹을 보고, GitHub나 사내 시스템은 MCP를 통해 조회한다. 큰 조사라면 서브에이전트를 나눠 병렬로 돌린다. 이 모든 흐름이 같은 세션 기록과 컨텍스트 안에 남는다.

도구 출력 자체도 모델 친화적으로 다듬어져 있다. 무작정 파일 전체를 쏟는 대신 행과 바이트 제한, 요약, artifact spill, 구조화된 메타데이터를 사용한다. 브라우저는 페이지 관찰과 조작을 지원하고, RPC는 JSONL로 외부 프로세스와 연결된다. 협업은 링크의 키로 암호화된 세션을 공유한다.

중요한 점은 이 기능들이 전부 같은 위험을 갖지 않는다는 것이다. read와 LSP 조회는 대체로 관찰이다. write는 작업공간을 바꾼다. bash, browser, task, SSH는 실행에 가깝다. MCP는 이름만 봐서는 읽기인지 운영 변경인지 알기 어렵다. 그래서 OMP는 도구에 `read`, `write`, `exec` tier를 붙이고 `allow`, `prompt`, `deny` 정책을 겹친다.

문제는 기본 정책이다. `tools.approvalMode`의 schema 기본값은 `yolo`다. 이 모드에서는 read, write, exec가 모두 자동 승인되고, 파괴적 셸 패턴이 `override` 경고를 만들어도 사용자가 별도로 bash를 `prompt`나 `deny`로 지정하지 않으면 질문 없이 진행된다. 기능은 강력하지만 안전한 조직 기본값과는 거리가 있다.

## 좋은 점

첫째, 프로젝트가 “모델이 똑똑하면 나머지는 대충이어도 된다”는 식으로 만들어지지 않았다. 출력 제한, 취소, timeout, 재시도, 세션 원자적 재작성, MCP 재연결, 브라우저 worker 종료, 서브에이전트 예산처럼 하네스에서 실제로 어려운 문제를 코드와 테스트로 다룬다.

둘째, 권한 모델의 한계를 숨기지 않는다. 승인 문서는 yolo가 기본이라는 사실, 안전 override도 yolo에서는 자동 승인된다는 사실, 서브에이전트가 headless yolo로 돈다는 사실을 명시한다. 확장 로딩 문서도 TypeScript와 JavaScript 모듈을 import해 factory를 실행한다고 설명한다. 위험한 구조를 안전하다고 포장하기보다 통제 지점을 노출한 편이다.

셋째, 협업 암호화는 실제 계약 테스트가 탄탄하다. 이번 검증에서 키가 다른 프레임과 변조 ciphertext를 거부하고, full/view 링크의 쓰기 토큰을 구분하며, 키를 URL path나 query가 아니라 fragment에 두는 테스트가 통과했다. relay가 평문 세션을 보는 구조가 아니라는 점은 분명한 장점이다.

넷째, 비밀정보 보호도 “문자열 몇 개 replace”보다 정교하다. 환경 변수 이름과 `secrets.yml`을 조합하고, 정규식과 고정값, reversible obfuscation과 one-way replacement를 나눈다. 같은 비밀은 turn이 달라도 안정된 placeholder가 되도록 해 prompt cache까지 고려한다.

다섯째, 릴리스 엔지니어링 신호가 좋다. TypeScript 검사와 다중 플랫폼 CI, Rust/native 빌드, Windows binary target, macOS 코드 서명, Homebrew formula의 asset digest가 따로 관리된다. 실제로 이번에 Biome이 3,393개 파일을 검사했고 모든 workspace 타입 검사가 통과했다. 비밀정보·협업 암호화·릴리스 관련 60개 테스트도 통과했다.

## 조심해야 할 점

문서를 읽는 것만으로도 기본 yolo와 확장 권한은 보인다. 그런데 코드를 따라가면 위험이 결합되는 방식이 더 선명해진다.

### 1. task 한 번의 승인이 생각보다 큰 실행권이다

서브에이전트는 UI가 없어서 `tools.approvalMode: yolo`로 실행된다. 부모의 `task` 승인이 권한 경계다. 여기까지는 공식 문서에도 나온다.

코드에서 더 확인되는 값은 규모다. 기본 최대 동시 실행은 32개, 기본 재귀 깊이는 2단계다. 일반 서브에이전트의 soft request budget은 200회이고 1.5배 지점부터 강제 종료 경로가 있지만, `task.maxRuntimeMs` 기본값은 `0`, 즉 시간 제한 없음이다.

따라서 task 한 번을 승인하는 것은 “조사 하나”를 승인하는 것과 다를 수 있다. 여러 모델 호출, 셸과 네트워크, 파일 변경이 동시에 확장될 수 있다. 팀 설정에서는 동시성, 재귀, wall-clock, 모델 비용, 도구 allowlist를 함께 줄여야 한다.

### 2. `write`라는 이름이 원격 작업의 위험도를 설명하지 못한다

MCP 도구는 별도 선언이 없으면 write tier로 분류된다. `write` approval mode는 read와 write를 자동 승인하고 exec만 묻는다.

로컬 문서 파일 수정과 “운영 키 회전”, “고객 데이터 갱신”, “이슈 닫기”가 모두 write라는 한 칸에 들어갈 수 있다는 뜻이다. tier는 기술적 능력의 분류이지 업무 영향도의 분류가 아니다. MCP는 서버별로 최소 권한 계정을 쓰고, 중요한 도구는 `tools.approval.<tool>`을 `prompt` 또는 `deny`로 고정해야 한다. 더 중요한 제약은 MCP 서버 자체의 RBAC와 감사 로그에 있어야 한다.

### 3. 확장의 exit guard는 샌드박스가 아니다

OMP는 `.omp/extensions`, 사용자 확장, hook, 설치 plugin을 찾아 Bun으로 동적 import하고 factory를 실행한다. loader는 오류를 모으고 일부 `process.exit` 실패를 방어한다. 하지만 확장은 여전히 같은 프로세스에서 파일, 환경 변수, 네트워크에 접근할 수 있는 코드다.

즉 “확장 하나가 기동을 죽이지 않게 했다”와 “확장이 격리됐다”는 전혀 다른 말이다. 낯선 저장소를 열 때 프로젝트 확장과 hook을 꺼야 하는 이유가 여기에 있다. 프로젝트의 `.omp` 디렉터리는 설정 폴더이면서 실행 가능한 공급망 경계다.

### 4. secret obfuscation은 DLP가 아니다

비밀정보 보호는 기본으로 꺼져 있다. 켜더라도 범위가 명확하다. 테스트를 보면 사용자 메시지, 도구 결과, 사용자 귀속 developer message를 가리지만 system prompt, tool schema, assistant message, inline image byte는 그대로 둔다. 8자보다 짧은 값도 오탐을 줄이기 위해 무시한다.

이것은 합리적인 text transform이지만 “비밀이 절대 provider로 나가지 않는다”는 보장은 아니다. 환경 변수 자체를 에이전트 프로세스에 많이 넘기지 않는 편이 낫고, 팀에서는 refresh token과 provider credential을 개발자 host에서 떼어내는 auth broker/gateway가 더 강한 경계다.

### 5. 브라우저 연결은 데이터뿐 아니라 사용자 세션의 가용성도 건드린다

브라우저 도구의 `app.path` 모드는 재사용 가능한 CDP endpoint가 없으면 같은 실행 파일 경로의 프로세스를 모두 종료한 뒤 debugging port를 붙여 다시 실행한다. 일상적으로 쓰던 Chrome이나 Electron 앱을 가리키면 작업 중이던 프로세스를 끊을 수 있다.

또 기존 CDP나 사용자가 넘긴 profile 인자를 쓰면 로그인된 웹 세션을 모델이 조작할 수 있다. 브라우저 자동화가 편리한 이유와 위험한 이유가 같다. 회사 계정이 로그인된 daily profile 대신 전용 automation profile이나 headless browser를 써야 한다.

### 6. 로컬 저장은 강하지만 보존 정책은 따로 설계해야 한다

긍정적인 부분부터 보면 `agent.db`는 디렉터리 `0700`, 파일 `0600`으로 권한을 강화한다. 반면 session JSONL과 blob의 일반 write 경로는 매번 같은 명시적 chmod를 적용하기보다 상위 디렉터리와 OS umask에 기대는 부분이 있다.

그리고 GC의 기본 cold archive는 30일 뒤 세션을 압축·보관하는 흐름이지 전사적인 삭제 SLA가 아니다. 최근 세션은 전역과 작업공간 단위로 남기고, collaboration guest도 참가한 세션의 replica를 자신의 endpoint에 저장한다. 디스크 암호화, backup 제외 규칙, 보존 기간, 안전한 삭제, 퇴사자 장비와 guest device 정책은 OMP 밖에서 정해야 한다.

### 7. 릴리스 검증과 기본 설치 경로 사이에 틈이 있다

릴리스 CI는 macOS binary 서명을 검증하고, Homebrew formula 생성기는 GitHub asset의 SHA-256 digest를 사용한다. 그런데 기본 `scripts/install.sh`의 binary 경로는 최신 release asset을 최종 설치 위치로 다운로드한 뒤 digest를 확인하지 않고 실행 권한을 준다.

GitHub TLS가 무의미하다는 뜻은 아니다. 다만 통제된 조직에서 기대하는 “pin한 버전의 기대 digest와 실제 파일을 대조한다”는 단계가 기본 curl 설치에는 없다. 가능하면 버전과 digest가 고정된 package manager·formula·내부 mirror를 쓰고, 설치 스크립트를 pipe로 바로 실행하지 않는 편이 낫다.

### 8. 자동화 모드에서는 프로세스 복구도 제품의 일부다

2026년 7월 12일 기준 open 상태인 issue #5194는 RPC stdin에 JSON이 아닌 한 줄이 들어오면 프로세스 전체가 종료된다고 보고한다. issue #4820은 긴 resumed TUI 세션의 JSC/WebKit footprint와 event-loop blocking을 다룬다. 반면 idle CPU issue #5192와 plugin upgrade issue #5189는 v16.4.5 릴리스 시점에 closed됐다.

여기서 읽어야 할 것은 “불안정하다” 한마디가 아니다. 대화형 사용과 무인 RPC worker는 필요한 복구 수준이 다르다는 점이다. 자동화라면 strict framing, supervisor, idempotent queue, checkpoint, 재시작, canary, rollback이 필요하다.

## 언제 쓰면 좋은가

OMP가 가장 잘 맞는 곳은 작업이 충분히 복잡해서 도구 사이 왕복이 병목인 환경이다.

- 낯선 대형 저장소에서 정의·참조·테스트·디버거를 오가며 원인을 찾아야 할 때
- 코드 수정 뒤 lint, typecheck, test, runtime smoke까지 같은 흐름으로 연결하고 싶을 때
- 모델이나 provider를 바꿔도 동일한 세션·도구 하네스를 유지하고 싶을 때
- 조사·구현·검토를 역할별로 나누되 사람이 최종 결과를 검토할 수 있을 때
- 작은 팀이 버전 pin, 격리, CI, 자격증명 정책을 직접 운영할 수 있을 때

반대로 단순 자동완성만 필요하거나, 모든 변경이 deterministic하고 감사 가능해야 하거나, 공개 입력이 곧바로 높은 권한의 도구로 이어지는 환경이라면 과한 선택일 수 있다. 그런 업무는 좁은 workflow engine이나 전용 API가 더 낫다.

내가 개인 개발 환경에 넣는다면 다음 기준선부터 시작한다.

```yaml
tools:
  approvalMode: always-ask
  approval:
    bash: prompt
    browser: prompt
    task: prompt
secrets:
  enabled: true
task:
  maxConcurrency: 2
  maxRecursionDepth: 1
  maxRuntimeMs: 900000
```

실제 key 이름과 지원 범위는 버전별 문서를 다시 확인해야 한다. 중요한 것은 예시를 복사하는 일이 아니라 **처음에는 좁게 시작한다**는 원칙이다. 낯선 저장소에서는 extension과 project MCP를 끄고, 전용 worktree와 automation profile을 사용한다.

팀 기준선은 설정 파일보다 아키텍처에 가깝다.

| 경계 | 권장 기준 |
| --- | --- |
| 실행 | 작업마다 새 worktree·container, 홈·SSH agent 미마운트, CPU/RAM/시간 제한 |
| 자격증명 | 최소 권한 token, broker/gateway 또는 제한된 sidecar, refresh token 분리 |
| 네트워크 | 모델 endpoint와 필요한 API만 egress 허용, browser lane 분리 |
| 변경 | main 직접 push 금지, 작은 diff, CI·secret scan·소유자 review |
| 저장 | endpoint 암호화, session·blob·log 보존/삭제 정책, guest device 통제 |
| 릴리스 | 버전·digest pin, canary, 회귀 테스트, rollback |

바로 전사 배포하는 대신 4주 정도의 파일럿으로 확인하는 편이 좋다.

| 단계 | 허용 범위 | 확인할 것 |
| --- | --- | --- |
| 준비 | 위협 모델과 기준선 수집 | 데이터 등급, 허용 provider, 금지 도구, 기존 lead time·CI·리워크 |
| 1주차 | read-only 분석과 테스트 계획 | 정확도, 근거 파일, 사람이 한 결과와의 차이 |
| 2주차 | 문서·테스트·작은 저위험 수정 | first-pass CI, 리뷰 수정 횟수, rollback |
| 3주차 | 서브에이전트 1~2개 | 총시간 절감, 비용, reviewer 병목, 충돌 |
| 4주차 | 자동화 lane 하나 | 재시작, idempotency, 정책 위반, 사람 handoff |

측정 항목에는 속도만 넣으면 안 된다. 작업당 모델 비용, 리뷰 시간, first-pass CI, 결함과 rollback, deny/prompt 빈도, 외부 egress, 프로세스 재시작, PR 크기까지 같이 봐야 한다. 작성 속도만 빨라지고 리뷰 대기열이 길어지면 팀 전체 생산성은 좋아진 것이 아니다.

## 주니어 개발자가 배울 점

OMP에서 가장 먼저 배울 점은 agent 품질이 모델 이름만으로 결정되지 않는다는 사실이다. 어떤 정보를 보여주고, 어떤 도구를 숨기고, 실패를 어떻게 제한하고, 결과를 어떻게 저장하는지가 실제 품질을 만든다.

두 번째는 권한의 이름을 믿지 말고 효과를 보라는 점이다. `write`라고 해서 항상 저위험은 아니다. 로컬 markdown 수정과 원격 운영 변경은 같은 write tier에 들어갈 수 있다. 보안 경계는 기술 분류와 업무 의미를 같이 봐야 한다.

세 번째는 방어 기능의 적용 범위를 읽는 습관이다. secret obfuscation이 있다고 끝이 아니다. 기본으로 켜져 있는지, 어떤 message type을 다루는지, 이미지와 system prompt는 어떻게 되는지 확인해야 한다. E2EE도 relay가 못 본다는 뜻이지 endpoint에 평문이 남지 않는다는 뜻은 아니다.

네 번째는 좋은 프로젝트를 평가할 때 실패 흔적도 보라는 점이다. OMP에는 취소, timeout, 원자적 session rewrite, MCP reconnect, browser worker kill, release asset 검증 같은 디테일이 많다. 이는 코드가 완벽하다는 증거가 아니라 실제 운영 문제를 만나고 고쳐왔다는 증거다.

마지막으로 자동화의 가치는 “사람을 없애는 것”보다 피드백 루프를 줄이는 데서 먼저 나온다. 코드 탐색, 수정, 테스트를 이어주는 데 agent를 쓰고, 권한 확대와 무인 실행은 증거가 쌓인 뒤 천천히 여는 편이 훨씬 건강하다.

## 내 결론

OMP는 장난감이 아니다. 코드 구조와 테스트 규모, 릴리스 엔지니어링, 도구 통합을 보면 현재 가장 야심찬 터미널 agent harness 중 하나라고 평가할 만하다. 숙련 개발자가 복잡한 저장소에서 쓰면 탐색과 검증 왕복을 줄여주는 실질적인 가치가 있다.

동시에 “설치하면 더 똑똑해지는 CLI” 정도로 배치하면 위험하다. 기본 yolo, headless subagent, in-process extension, MCP credential, browser attach, 로컬 session, 빠른 release cadence를 하나의 시스템으로 봐야 한다. 각각의 기능은 통제 수단을 갖고 있지만, 그 통제 수단을 조합하고 운영하는 책임은 사용자와 팀에 남는다.

개인에게는 전용 프로필과 항상 묻는 승인 모드, 좁은 도구, 격리된 worktree로 시작하는 것을 추천한다. 팀에는 read-only 파일럿부터 권한다. 전사 배포나 무인 CI는 container, broker, egress policy, supervisor, CI/review gate, retention, canary가 준비된 뒤의 일이다.

한 문장으로 정리하면 이렇다. **OMP는 충분히 쓸 만하다. 다만 생산성을 높여주는 앱이 아니라, 생산성과 사고 반경을 함께 키우는 실행 플랫폼으로 다뤄야 한다.**
