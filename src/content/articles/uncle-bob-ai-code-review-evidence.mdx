AI가 만든 코드를 사람이 한 줄도 읽지 않아도 된다는 주장은 현재 근거로는 성립하지 않는다. 다만 **저위험 변경에서 구현 줄 단위 검토를 줄이고, 실행 가능한 명세와 독립 검증에 더 많은 시간을 쓰자**는 주장이라면 실용적인 방향이다.

Uncle Bob Martin은 2026년 7월 23일 게시에서, 에이전트가 쓴 코드를 읽지 않고 단위 테스트·Gherkin·QA 절차·품질 지표·mutation testing·커버리지 같은 제약으로 신뢰한다는 전략을 말했다. 그 게시 자체는 CRAP이나 `crap4java`를 이름으로 들지 않는다. 이 글은 그 제약 묶음의 한 공개 구현인 `crap4java`가 실제로 무엇을 잡는지 본다. CRAP은 센서일 뿐이고, 코드를 읽지 않아도 된다는 일반 규칙은 아니다.

이 글의 식·게이트·파서 동작은 2026년 8월 26일 기준으로 `unclebob/crap4java` 기본 브랜치와 명세, JaCoCo 문서를 다시 대조했다. HEAD는 여전히 커밋 `69b5612`(2026-03-13, “Refresh Java tool READMEs”)다. Maven은 이 환경에 없어 업스트림 JUnit은 실행하지 않았다. 이 도구는 순환 복잡도와 JaCoCo 명령어 커버리지를 CRAP 점수로 합친다. 유용한 위험 신호지만, 보안·아키텍처·데이터 손실 같은 시스템 위험을 판정하는 코드 리뷰 대체재는 아니다.

## 먼저 알아야 할 개념

CRAP은 Change Risk Anti-Patterns의 약자로, 메서드의 복잡도와 테스트 커버리지를 결합한다. `crap4java`가 구현한 식은 다음과 같다.

`CRAP = CC² × (1 - coverage)³ + CC`

여기서 `CC`는 순환 복잡도이고 `coverage`는 0과 1 사이의 비율이다. 분기가 많아 복잡한 메서드라도 테스트가 충분하면 점수가 내려가고, 복잡하면서 테스트가 부족하면 크게 올라간다.

이 점수는 “코드가 맞다”를 증명하지 않는다. 테스트가 실행한 명령어 비율과 제어 흐름의 복잡도를 이용해 **변경 위험이 높아 보이는 메서드**를 찾는 휴리스틱이다. 잘못된 기대값을 검사하는 테스트가 100% 커버리지를 만들어도 로직은 틀릴 수 있다.

## 실제 구조

현재 저장소의 CLI는 Java 17을 대상으로 하고 JUnit 5.10.2와 JaCoCo 0.8.12를 사용한다. 분석 흐름은 다음과 같다.

1. JDK 컴파일러 트리 API로 소스의 메서드와 복잡도를 수집한다.
2. JaCoCo XML에서 클래스·메서드·라인별 명령어 커버리지를 읽는다.
3. `class#method:line` 키로 두 결과를 결합한다.
4. 숫자 점수 중 최대값이 임계값 8.0을 초과하면 실패한다.

현재 파서는 본문이나 반환형이 없는 노드를 건너뛴다. 명세도 생성자, 추상 메서드, 익명 클래스 메서드를 제외한다. 메서드 방문 뒤에는 내부로 내려가지 않아 지역 클래스 메서드도 별도 메서드로 수집되지 않는다. 반면 람다 안의 분기는 바깥 메서드의 복잡도에 포함된다.

2026년 7월 26일의 임시 Java 표본 하네스는 바깥 메서드와 멤버 내부 클래스 메서드를 각각 복잡도 2로 수집했고, 생성자·익명 클래스 메서드·지역 클래스 메서드는 결과에 없었다. JaCoCo 보고서가 없을 때 파서는 빈 맵을 반환했고, 점수를 계산할 수 없는 메서드는 `null`이 됐다. 숫자 점수만 모은 최대값은 0.0, 임계값 판정은 통과였다. 이 수치를 이번 작업에서 다시 실행하지는 않았다. 같은 커밋의 계산기·파서·명세는 그 해석과 맞는다.

이것은 구현과 명세가 어긋난 우연한 버그라고 단정할 수 없다. 저장소의 명세도 “숫자 점수가 하나도 없으면 최대값은 0이고 통과”라고 정의한다. 다만 커버리지 명령 자체가 실패하면 도구는 바로 중단한다. CI 품질 게이트로 쓸 때 보고서 부재를 통과로 두는 것은 **fail-open 정책**이므로 팀이 의식적으로 선택해야 한다.

## 핵심 기능

CRAP 임계값 8.0을 기준으로 필요한 커버리지를 식에서 역산하면 다음과 같다.

| 복잡도(CC) | 점수 8 이하에 필요한 최소 커버리지 |
| ---: | ---: |
| 1–2 | 0% |
| 3 | 약 17.8% |
| 4 | 약 37.1% |
| 5 | 약 50.7% |
| 6 | 약 61.9% |
| 7 | 약 72.7% |
| 8 | 100% |
| 9 이상 | 커버리지와 무관하게 불가능 |

이 표가 보여 주는 것은 CRAP의 강점과 한계다. 복잡도 9 이상은 테스트가 많아도 임계값을 넘으므로 분해를 강하게 유도한다. 반대로 복잡도 1~2의 단순한 메서드는 테스트가 없어도 통과한다. 그 단순한 메서드가 권한 체크를 빠뜨렸는지, 돈을 잘못 반올림하는지는 지표가 알 수 없다.

실무에서는 CRAP을 다음 검증망의 한 센서로 두는 편이 좋다.

- 실행 가능한 인수 조건과 예제
- 단위·통합·계약 테스트
- 분기 커버리지와 경계값 테스트
- mutation testing 또는 property-based testing
- 정적 분석, 타입 검사, 의존성·비밀정보 검사
- 배포 전후 관측성과 롤백 조건
- 위험도에 따른 사람 리뷰

## 좋은 점

이 접근의 장점은 리뷰를 “코딩 취향”에서 검증 가능한 실패 조건으로 옮긴다는 데 있다. 복잡한데 테스트가 없는 메서드를 자동으로 찾고, 임계값을 CI에 고정하면 팀의 최소 기준이 일관된다.

AI 코드에서는 특히 유용하다. 생성 속도가 사람의 읽기 속도보다 빠르기 때문에 모든 줄을 같은 깊이로 읽는 방식은 병목이 된다. 자동 지표로 후보를 좁히고 사람이 보안 경계와 설계 결정을 집중 검토하면 리뷰 자원을 더 위험한 곳에 쓸 수 있다.

또한 공식 JaCoCo 문서가 설명하듯 명령어 커버리지는 디버그 정보 없이도 계산할 수 있어 수집이 안정적이다. 다만 이것이 분기 커버리지와 같다는 뜻은 아니다.

## 조심해야 할 점

첫 번째 사각지대는 **커버리지의 종류와 테스트의 질**이다. 현재 점수는 JaCoCo의 `INSTRUCTION` 카운터를 사용한다. 모든 참·거짓 경로를 검사했는지, assertion이 올바른지, 예외와 경쟁 조건을 다뤘는지는 알 수 없다. mutation testing은 테스트가 인위적 결함을 잡는지 확인해 이 공백 일부를 보완할 수 있다.

두 번째는 **소스와 커버리지의 결합 방식**이다. 정확한 키가 없으면 같은 클래스와 같은 메서드 이름 중 가장 가까운 라인을 찾는다. JVM 시그니처를 쓰지 않기 때문에 오버로드, 합성 메서드, 람다로 라인이 달라진 경우 다른 커버리지를 붙일 가능성이 있다.

세 번째는 **분석 대상 누락**이다. 생성자, 익명·지역 클래스 메서드가 빠지고 람다 분기는 바깥 메서드에 합산된다. 점수의 단위가 개발자가 생각하는 메서드 경계와 다를 수 있다.

네 번째는 **보고서 부재의 통과**다. 커버리지 명령이 실패하면 분석은 중단된다. 하지만 명령이 끝난 뒤 JaCoCo XML이 없으면 경고만 내고 커버리지는 `N/A`가 되며, 숫자 점수가 하나도 없으면 최대값 0으로 통과한다. 품질 게이트라면 `unknown`을 별도 상태로 만들고, 보고서가 필수인 CI에서는 실패시키는 정책이 더 안전하다.

마지막으로 CRAP은 아래 위험을 보지 못한다.

- 인증·인가 누락과 개인정보 노출
- SQL 마이그레이션과 데이터 복구 가능성
- 동시성, 재시도, 멱등성
- 공개 API 호환성과 아키텍처 경계
- 성능, 비용, 로그의 민감정보
- 테스트 자체의 잘못된 오라클

## 언제 쓰면 좋은가

순수 함수, 내부 변환기, 되돌리기 쉬운 저위험 기능처럼 실패 범위가 작고 독립 테스트를 강하게 만들 수 있는 곳에서는 줄 단위 리뷰를 줄여도 된다. 이때도 변경의 목적, 공개 계약, 테스트 결과, 지표의 미측정 여부는 검토해야 한다.

반대로 인증·결제·개인정보·암호화·DB 마이그레이션·분산 처리·공개 API·안전 관련 코드는 사람이 설계와 구현을 함께 봐야 한다. 자동 테스트가 많다는 이유만으로 위험 모델과 복구 계획을 생략할 수 없다.

## 주니어 개발자가 배울 점

첫째, 숫자의 식을 직접 읽어야 한다. “임계값 8”만 외우면 복잡도 2는 무테스트로 통과하고 복잡도 9는 완전 커버리지로도 실패한다는 사실을 놓친다.

둘째, 결측값 정책은 기능만큼 중요하다. 측정할 수 없을 때 통과할지, 경고할지, 실패할지를 명세에 적어야 한다.

셋째, 테스트 커버리지는 테스트 품질이 아니다. 실패를 주입해 테스트가 실제로 잡는지 확인하고, 경계값과 잘못된 입력을 설계해야 한다.

넷째, 코드 리뷰의 목적은 코드를 읽는 행위 자체가 아니라 위험을 발견하고 책임질 근거를 남기는 것이다. 자동화가 더 잘 보는 영역과 사람이 더 잘 보는 영역을 분리하는 능력이 중요하다.

## 내 결론

나는 “AI 코드를 읽지 말자”보다 **“위험을 읽자”**는 표현이 정확하다고 본다. CRAP 같은 지표는 복잡성과 테스트 공백을 찾는 훌륭한 필터지만, 품질 보증서가 아니다.

실무 도입 순서는 간단하다. 먼저 현재 코드에서 지표를 관찰만 하고, 누락·오탐을 확인한다. 다음으로 커버리지 보고서가 없을 때 실패하도록 정책을 정한다. 이후 저위험 변경부터 자동 검증 중심 리뷰를 실험하고, 고위험 변경에는 사람의 설계·보안·운영 검토를 유지한다. 리뷰 시간을 줄이는 목표보다 **놓친 위험을 측정할 수 있는 구조**가 먼저다.
