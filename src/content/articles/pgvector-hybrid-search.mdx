RAG 검색을 처음 만들 때 흔히 `LIKE '%검색어%'`나 단순 키워드 검색부터 떠올린다. 하지만 사용자는 항상 문서에 들어 있는 단어 그대로 검색하지 않는다. “카드 결제 오류”라고 입력했을 때 실제 문서는 “신용카드로 결제하려는데 실패합니다”일 수 있고, 반대로 `ERR_PAYMENT_403`처럼 정확한 문자열이 중요한 검색어도 있다.

그래서 실무 검색은 보통 두 가지 축을 함께 본다. 하나는 단어가 실제로 들어 있는지 보는 FTS, 다른 하나는 문장의 의미가 가까운지 보는 벡터 검색이다. 이 둘을 섞고, 마지막 순위를 안정적으로 합치는 방식이 하이브리드 검색이다.

이 글은 PostgreSQL과 Spring Boot는 어느 정도 알지만 `pgvector`, ANN 인덱스, RRF가 낯선 주니어 개발자를 기준으로 정리한다. 목표는 쿼리를 외우는 것이 아니라, 왜 이런 구조가 필요한지 이해하는 것이다.

## 한눈에 보는 검색 흐름

사용자가 검색창에 이렇게 입력했다고 하자.

```text
카드 결제 오류
```

RAG 검색 시스템은 보통 다음 순서로 움직인다.

```text
사용자 검색어
  ↓
검색어를 embedding vector로 변환
  ↓
PostgreSQL에서 두 검색 실행
  ├─ FTS 검색: 정확한 단어 기반 검색
  └─ Vector 검색: 의미 기반 검색
  ↓
두 결과를 RRF 같은 방식으로 합침
  ↓
최종 top K 문서를 LLM context에 넣음
```

여기서 FTS와 벡터 검색은 경쟁 관계가 아니다. 역할이 다르다.

| 검색 방식 | 잘하는 것 | 예시 |
| --- | --- | --- |
| FTS | 정확한 단어, 코드, 제품명, 에러 문자열 찾기 | `카드`, `ERR_PAYMENT_403` |
| Vector Search | 표현은 달라도 의미가 가까운 문서 찾기 | `결제가 실패해요`, `결제 수단 등록이 안 됩니다` |

FTS만 쓰면 표현이 조금 바뀐 문서를 놓치고, 벡터 검색만 쓰면 정확한 식별자 검색이 약해질 수 있다. 하이브리드 검색은 이 약점을 서로 보완한다.

## 예제 테이블

예제에서는 문서 본문과 embedding을 같은 테이블에 둔다.

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE doc_embeddings (
    id bigserial PRIMARY KEY,
    content text NOT NULL,
    embedding vector(1536)
);
```

`vector(1536)`은 embedding 차원 수다. 실제 차원은 사용하는 embedding 모델에 따라 달라진다. 중요한 점은 테이블 컬럼 차원과 검색 벡터 차원이 반드시 같아야 한다는 것이다.

```text
테이블 컬럼: vector(1536)
검색 벡터: 1536차원
```

둘이 다르면 검색 품질이 떨어지는 정도가 아니라 쿼리 자체가 실패한다.

## KNN 벡터 검색부터 시작하기

KNN은 `K-Nearest Neighbors`의 약자다. 벡터 검색에서는 “검색 문장 벡터와 가장 가까운 문서 벡터 K개를 찾는다”는 뜻이다.

기본 쿼리는 이렇게 생겼다.

```sql
SELECT id, content
FROM doc_embeddings
ORDER BY embedding <=> '[0.82, 0.14, 0.63, 0.45, 0.71, 0.28, 0.56, 0.39]'
LIMIT 5;
```

이 쿼리는 모든 문서의 `embedding`과 검색 벡터 사이의 거리를 계산한 뒤, 가장 가까운 5개를 가져온다.

여기서 `<=>`는 pgvector의 cosine distance 연산자다. 가장 많이 하는 실수는 이 값을 유사도라고 생각하는 것이다.

```text
<=> 는 유사도가 아니라 거리다.
값이 작을수록 더 가깝다.
```

그래서 정렬은 오름차순이다.

```sql
ORDER BY embedding <=> query_embedding
```

유사도 점수처럼 보고 싶다면 보통 이렇게 바꿔서 보여준다.

```sql
1 - (embedding <=> query_embedding) AS vec_score
```

하지만 내부 랭킹과 인덱스 사용을 생각할 때는 “작은 distance가 좋은 결과”라는 감각을 유지하는 편이 낫다.

## 왜 인덱스가 필요한가

인덱스가 없으면 PostgreSQL은 전체 테이블을 훑는다.

```text
Seq Scan
  → 모든 row의 embedding 거리 계산
  → 거리 기준 정렬
  → LIMIT 5
```

문서가 1천 개라면 큰 문제가 아닐 수 있다. 하지만 10만 개, 100만 개, 1000만 개가 되면 매 검색마다 전체 벡터를 비교하는 방식은 부담이 크다.

그래서 ANN 인덱스를 쓴다. ANN은 `Approximate Nearest Neighbor`다. 정확히 모든 벡터를 비교하지 않고, 가까울 가능성이 높은 후보를 빠르게 찾는다.

```text
정확도 일부를 양보하고 검색 속도를 얻는 방식
```

pgvector에서 자주 보는 ANN 인덱스는 IVFFLAT과 HNSW다.

## IVFFLAT: 가까운 방만 들어가서 찾기

IVFFLAT은 전체 벡터를 여러 클러스터로 나눠 저장한다. 쉽게 말하면 전체 문서를 여러 방으로 나누고, 검색할 때 검색 벡터와 가까운 방만 들어가서 찾는 방식이다.

```sql
CREATE INDEX idx_doc_embedding_ivfflat
ON doc_embeddings
USING ivfflat (embedding vector_cosine_ops)
WITH (lists = 100);
```

여기서 `lists`는 클러스터 개수다.

| 설정 | 의미 |
| --- | --- |
| `lists`가 너무 작음 | 한 클러스터에 데이터가 많아 검색이 느려질 수 있음 |
| `lists`가 너무 큼 | 클러스터가 잘게 나뉘어 유사 문서를 놓칠 수 있음 |
| 적절한 `lists` | 속도와 recall 사이의 균형 |

검색할 때는 `probes`로 몇 개의 클러스터를 볼지 정한다.

```sql
SET ivfflat.probes = 10;
```

```text
lists = 100, probes = 1
→ 가장 가까운 클러스터 1개만 검색

lists = 100, probes = 10
→ 가까운 클러스터 10개 검색

lists = 100, probes = 100
→ 모든 클러스터 검색에 가까워짐
```

`probes`가 낮으면 빠르지만 놓치는 문서가 생길 수 있다. `probes`가 높으면 느려지지만 recall이 좋아진다.

![IVFFLAT 클러스터 검색 흐름](/images/articles/pgvector-hybrid-search-ivfflat-cluster.png)

그림에서 `전체 벡터`는 DB에 저장된 모든 문서 embedding이다. 이 벡터들이 여러 클러스터로 나뉘고, 검색 벡터는 그중 가까운 클러스터로 들어간다. 마지막에는 선택된 클러스터 안에서만 KNN 검색을 한다.

주의할 점이 있다. 그림에는 `카드 관련`, `이체/송금/급여`처럼 사람이 읽기 쉬운 이름을 붙였지만, 실제 IVFFLAT이 사람이 정한 카테고리 이름으로 묶는 것은 아니다. embedding 공간에서 가까운 벡터끼리 자동으로 묶인다.

```text
텍스트 카테고리 기준으로 직접 분류하는 것 ❌
벡터 공간의 거리 기준으로 묶는 것 ✅
```

IVFFLAT은 인덱스 구축이 비교적 빠르고 메모리 사용량도 낮은 편이다. 대신 클러스터 설정과 `probes` 값에 따라 진짜 가까운 문서를 놓칠 수 있다. 데이터 분포가 많이 바뀌는 서비스라면 인덱스 품질도 주기적으로 확인해야 한다.

## HNSW: 그래프를 타고 가까운 벡터 찾기

HNSW는 `Hierarchical Navigable Small World`의 약자다. IVFFLAT이 클러스터를 찾아 들어가는 방식이라면, HNSW는 벡터들을 그래프처럼 연결해두고 검색할 때 가까운 노드를 따라간다.

```text
문서 벡터 A ─ 문서 벡터 B ─ 문서 벡터 C
      │              │
문서 벡터 D ─ 문서 벡터 E
```

인덱스는 이렇게 만든다.

```sql
CREATE INDEX idx_doc_embedding_hnsw
ON doc_embeddings
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

주요 설정은 세 가지다.

| 설정 | 의미 | 커질 때의 효과 |
| --- | --- | --- |
| `m` | 각 노드가 연결할 이웃 수 | 정확도는 좋아질 수 있지만 인덱스가 커짐 |
| `ef_construction` | 인덱스 생성 시 넓게 볼 후보 수 | 생성은 느려지고 품질은 좋아질 수 있음 |
| `ef_search` | 검색 시 넓게 볼 후보 수 | 검색은 느려지고 recall은 좋아질 수 있음 |

검색 시에는 보통 트랜잭션 안에서 `SET LOCAL`로 조절한다.

```sql
BEGIN;

SET LOCAL hnsw.ef_search = 100;

SELECT id, content
FROM doc_embeddings
ORDER BY embedding <=> '[0.82, 0.14, 0.63, 0.45, 0.71, 0.28, 0.56, 0.39]'
LIMIT 5;

COMMIT;
```

초기 RAG 서비스라면 HNSW를 먼저 검토하는 경우가 많다. 검색 품질이 대체로 좋고, 실시간 insert에도 비교적 잘 맞기 때문이다. 다만 HNSW는 인덱스 생성이 더 느리고 메모리 사용량도 더 크다.

| 항목 | IVFFLAT | HNSW |
| --- | --- | --- |
| 핵심 구조 | 클러스터/list | 계층형 그래프 |
| 검색 방식 | 가까운 클러스터만 탐색 | 그래프를 따라 가까운 노드 탐색 |
| 인덱스 생성 속도 | 빠른 편 | 느린 편 |
| 메모리 사용량 | 적은 편 | 많은 편 |
| 검색 정확도 | 설정에 따라 낮을 수 있음 | 일반적으로 높은 편 |
| 주요 튜닝값 | `lists`, `probes` | `m`, `ef_construction`, `ef_search` |
| 추천 상황 | 데이터가 비교적 정적이고 대량 | 검색 품질이 중요하고 데이터 추가가 있음 |

## FTS: 의미가 아니라 단어를 찾기

FTS는 `Full-Text Search`다. 벡터 검색이 의미 기반 검색이라면, FTS는 키워드 기반 검색이다.

```sql
SELECT
    id,
    content,
    ts_rank(
        to_tsvector('simple', content),
        plainto_tsquery('simple', '카드 결제 오류')
    ) AS fts_score
FROM doc_embeddings
WHERE to_tsvector('simple', content) @@ plainto_tsquery('simple', '카드 결제 오류')
ORDER BY fts_score DESC
LIMIT 5;
```

핵심 함수와 연산자는 세 가지다.

| 요소 | 역할 |
| --- | --- |
| `to_tsvector` | 문서 내용을 검색 가능한 토큰 구조로 바꿈 |
| `plainto_tsquery` | 일반 사용자 입력을 FTS query로 바꿈 |
| `@@` | 문서와 query가 매칭되는지 검사 |

데이터가 많다면 매번 `to_tsvector`를 계산하지 말고 generated column과 GIN 인덱스를 쓰는 편이 좋다.

```sql
ALTER TABLE doc_embeddings
ADD COLUMN content_tsv tsvector
GENERATED ALWAYS AS (
    to_tsvector('simple', coalesce(content, ''))
) STORED;

CREATE INDEX idx_doc_content_tsv
ON doc_embeddings
USING GIN (content_tsv);
```

이후 쿼리는 더 단순해진다.

```sql
SELECT
    id,
    content,
    ts_rank(content_tsv, plainto_tsquery('simple', '카드 결제 오류')) AS fts_score
FROM doc_embeddings
WHERE content_tsv @@ plainto_tsquery('simple', '카드 결제 오류')
ORDER BY fts_score DESC
LIMIT 5;
```

한국어에서는 주의가 필요하다. PostgreSQL의 `simple` 설정은 한국어 형태소 분석기가 아니다. 공백으로 나뉜 `카드 결제 오류`는 어느 정도 맞을 수 있지만, `카드결제`, `신용카드를`, `결제했습니다` 같은 표현에서는 기대와 다를 수 있다.

한국어 검색 품질이 중요하면 다음 선택지도 검토해야 한다.

| 선택지 | 적합한 상황 |
| --- | --- |
| PostgreSQL FTS `simple` | 간단한 공백 기반 검색으로 충분할 때 |
| `pg_trgm` | 부분 문자열 검색이 중요할 때 |
| PGroonga | 한국어, 일본어, 중국어 검색 품질이 중요할 때 |
| OpenSearch/Elasticsearch | analyzer, 운영 기능, 검색 튜닝이 중요할 때 |

## Hybrid Search: 두 검색 결과를 합치기

FTS와 벡터 검색을 각각 실행한 뒤 합치는 가장 단순한 방식은 점수를 더하는 것이다.

```sql
ORDER BY fts_score + vec_score DESC
```

하지만 이 방식은 곧 한계가 온다. `ts_rank`와 cosine similarity는 같은 척도의 점수가 아니다.

| id | fts_score | vec_score |
| --- | ---: | ---: |
| 1 | 0.05 | 0.89 |
| 2 | 0.30 | 0.50 |
| 3 | 0.01 | 0.95 |

여기서 `fts_score = 0.30`이 `vec_score = 0.89`보다 강한 신호인지 단순 비교하기 어렵다. 점수의 출신이 다르기 때문이다.

그래서 실무에서는 점수 자체보다 순위를 합치는 RRF를 자주 쓴다.

## RRF: 점수 대신 순위를 합치기

RRF는 `Reciprocal Rank Fusion`이다. 핵심은 간단하다.

```text
점수 기반 결합:
fts_score + vec_score

순위 기반 결합:
1 / (k + fts_rank) + 1 / (k + vec_rank)
```

보통 `k = 60`을 기본값처럼 많이 쓴다.

```text
RRF Score = 1 / (60 + rank)
```

FTS에서 1등이고 벡터 검색에서 2등인 문서는 한쪽에서만 1등인 문서보다 안정적으로 높은 점수를 받는다. RRF는 “여러 검색 방식에서 골고루 상위권인 문서”를 좋아한다.

실무에서는 최종 top 5를 보여주더라도 후보는 더 넉넉히 가져오는 편이 좋다.

```text
FTS top 50
Vector top 50
  ↓
RRF로 합침
  ↓
최종 top 5 반환
```

후보를 너무 작게 잡으면 RRF로 좋아질 수 있는 문서를 너무 일찍 버린다.

## RRF 기반 SQL 예시

아래 쿼리는 FTS 후보 50개와 벡터 후보 50개를 가져온 뒤 RRF로 최종 순위를 만든다.

```sql
WITH
query AS (
    SELECT
        plainto_tsquery('simple', '카드 결제 오류') AS text_query,
        '[0.82, 0.14, 0.63, 0.45, 0.71, 0.28, 0.56, 0.39]'::vector AS query_embedding
),
fts_candidates AS (
    SELECT
        d.id,
        d.content,
        ts_rank(d.content_tsv, q.text_query) AS fts_score
    FROM doc_embeddings d
    CROSS JOIN query q
    WHERE d.content_tsv @@ q.text_query
    ORDER BY fts_score DESC
    LIMIT 50
),
fts_ranked AS (
    SELECT
        id,
        content,
        row_number() OVER (ORDER BY fts_score DESC) AS fts_rank
    FROM fts_candidates
),
vec_candidates AS (
    SELECT
        d.id,
        d.content,
        d.embedding <=> q.query_embedding AS distance
    FROM doc_embeddings d
    CROSS JOIN query q
    ORDER BY d.embedding <=> q.query_embedding
    LIMIT 50
),
vec_ranked AS (
    SELECT
        id,
        content,
        row_number() OVER (ORDER BY distance ASC) AS vec_rank
    FROM vec_candidates
)
SELECT
    coalesce(f.id, v.id) AS id,
    coalesce(f.content, v.content) AS content,
    f.fts_rank,
    v.vec_rank,
    round((
        coalesce(1.0 / (60 + f.fts_rank), 0) +
        coalesce(1.0 / (60 + v.vec_rank), 0)
    )::numeric, 6) AS rrf_score
FROM fts_ranked f
FULL OUTER JOIN vec_ranked v ON f.id = v.id
ORDER BY rrf_score DESC
LIMIT 5;
```

`FULL OUTER JOIN`을 쓰는 이유는 양쪽 결과를 모두 살리기 위해서다. FTS에만 나온 문서도 있고, 벡터 검색에만 나온 문서도 있다. `COALESCE`는 한쪽에만 있는 값의 `NULL`을 처리한다.

운영 코드에서는 검색어와 embedding을 문자열로 직접 붙이지 말고 파라미터 바인딩을 써야 한다. 또한 candidate 개수, `ef_search`, `probes`, 최종 `LIMIT`은 실제 데이터와 latency budget으로 튜닝해야 한다.

## Spring Boot에서는 어디에 둘까

Spring Boot에서는 검색 흐름을 보통 이렇게 나눈다.

```text
SearchController
  ↓
SearchService
  ↓
EmbeddingClient
  ↓
DocumentSearchRepository
  ↓
PostgreSQL Hybrid Search Query
```

`SearchController`는 HTTP 요청과 응답을 다룬다. `SearchService`는 검색어 validation, embedding 생성, 검색 실행, 결과 후처리를 조율한다. `EmbeddingClient`는 외부 embedding 모델 호출을 감싼다. `DocumentSearchRepository`는 SQL을 실행한다.

결과 모델은 단순하게 시작할 수 있다.

```java
public record SearchResult(
    Long id,
    String content,
    Integer ftsRank,
    Integer vectorRank,
    BigDecimal rrfScore
) {}
```

복잡한 하이브리드 검색 SQL은 일반 JPA 메서드 이름으로 표현하기 어렵다. `JdbcTemplate`, `NamedParameterJdbcTemplate`, jOOQ, MyBatis, native query 중 하나를 명시적으로 선택하는 편이 낫다. 검색 품질과 성능 튜닝이 중요하다면 SQL이 잘 보이는 도구가 운영에 유리하다.

## 운영 체크리스트

첫 번째는 벡터 차원이다.

```text
embedding 컬럼 차원과 query vector 차원이 같은가?
```

두 번째는 operator class와 검색 연산자 일치다.

| 목적 | 인덱스 operator class | 검색 연산자 |
| --- | --- | --- |
| Cosine distance | `vector_cosine_ops` | `<=>` |
| L2 distance | `vector_l2_ops` | `<->` |
| Inner product | `vector_ip_ops` | `<#>` |

cosine 인덱스를 만들었다면 검색도 cosine 연산자를 써야 한다.

```sql
CREATE INDEX idx_doc_embedding_hnsw
ON doc_embeddings
USING hnsw (embedding vector_cosine_ops);

SELECT id, content
FROM doc_embeddings
ORDER BY embedding <=> :query_embedding
LIMIT 5;
```

세 번째는 실행 계획이다.

```sql
EXPLAIN ANALYZE
SELECT id, content
FROM doc_embeddings
ORDER BY embedding <=> :query_embedding
LIMIT 5;
```

확인할 것은 인덱스 사용 여부만이 아니다. 실제 실행 시간, rows estimate와 actual rows 차이, candidate 수, sort 비용을 같이 봐야 한다. 작은 테이블에서는 PostgreSQL이 Seq Scan을 선택하는 것이 정상일 수도 있다.

네 번째는 대량 데이터 적재 후 통계 갱신이다.

```sql
ANALYZE doc_embeddings;
```

다섯 번째는 운영 중 인덱스 생성 절차다. 큰 테이블에서는 일반 `CREATE INDEX`가 부담이 될 수 있으므로 `CONCURRENTLY`를 검토한다.

```sql
CREATE INDEX CONCURRENTLY idx_doc_embedding_hnsw
ON doc_embeddings
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);
```

단, `CREATE INDEX CONCURRENTLY`는 트랜잭션 블록 안에서 쓸 수 없는 등 제약이 있다. 마이그레이션 도구와 운영 절차에 맞춰 별도 계획을 잡아야 한다.

## 주니어가 자주 하는 실수

첫째, `<=>`를 유사도라고 착각한다. `<=>`는 cosine distance이고 작을수록 좋다.

둘째, 인덱스 operator class와 검색 연산자를 다르게 쓴다. `vector_cosine_ops` 인덱스를 만들고 `<->`로 검색하면 의도와 다르다.

셋째, 최종 5개를 보여준다는 이유로 후보도 5개만 가져온다.

```text
나쁜 예:
FTS top 5 + Vector top 5 → RRF

더 나은 예:
FTS top 50 + Vector top 50 → RRF → 최종 top 5
```

넷째, FTS 점수와 벡터 점수를 그냥 더한다. 초기 실험은 가능하지만, 검색 품질이 중요해지면 RRF나 정규화 전략을 검토해야 한다.

다섯째, 한국어 FTS 품질을 과신한다. `simple`은 한국어 형태소 분석기가 아니다.

여섯째, 인덱스가 있는데 Seq Scan이 나오면 무조건 문제라고 생각한다. 작은 테이블에서는 Seq Scan이 더 빠를 수 있고, PostgreSQL 플래너가 그 선택을 하는 것이 자연스럽다.

## 추천 기본 구성

처음 RAG 검색 시스템을 만든다면 다음 구성을 우선 검토할 만하다.

```text
PostgreSQL + pgvector
  ├─ HNSW vector index
  ├─ FTS GIN index
  └─ RRF hybrid ranking
```

기본 인덱스는 이렇게 시작할 수 있다.

```sql
CREATE INDEX idx_doc_embedding_hnsw
ON doc_embeddings
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 64);

CREATE INDEX idx_doc_content_tsv
ON doc_embeddings
USING GIN (content_tsv);
```

그리고 검색 흐름은 이렇게 잡는다.

```text
1. 사용자가 검색어 입력
2. 검색어 embedding 생성
3. FTS top N 검색
4. Vector top N 검색
5. RRF로 랭킹 통합
6. 최종 top K 반환
7. RAG라면 top K 문서를 LLM context에 삽입
```

한 줄로 정리하면 이렇다. 벡터 검색은 의미를 찾고, FTS는 단어를 찾고, 하이브리드 검색은 둘을 합쳐 결과를 안정화한다. IVFFLAT은 클러스터를 찾아 들어가는 방식이고, HNSW는 그래프를 타고 가까운 벡터를 찾는 방식이다. 점수 합산은 위험할 수 있고, RRF는 순위 기반이라 하이브리드 검색에서 실용적이다.
