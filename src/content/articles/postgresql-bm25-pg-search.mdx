검색 기능을 처음 만들 때는 `LIKE '%카드 결제%'`로 시작하기 쉽다. 데이터가 적고 관리자 페이지에서 가끔 쓰는 정도라면 이 방식도 당장은 동작한다. 하지만 사용자가 검색창에 기대하는 것은 단순 포함 여부가 아니다. `카드 결제`를 검색했을 때 정말 관련 있는 거래가 먼저 나오고, `결제했다`처럼 어미가 붙은 표현도 어느 정도 잡히길 기대한다.

이 지점부터 검색은 문자열 조건이 아니라 랭킹 문제로 바뀐다. PostgreSQL 기본 FTS는 문장을 토큰화하고 GIN 인덱스로 빠르게 찾는 기반을 제공한다. ParadeDB의 `pg_search`는 여기에 BM25 기반 랭킹과 tokenizer 구성을 붙여 PostgreSQL 안에서 검색엔진에 가까운 흐름을 만들 수 있게 해준다.

이 글은 SQL과 PostgreSQL 기본 CRUD를 아는 주니어 개발자를 기준으로 정리한다. 목표는 문법을 외우는 것이 아니라, `FTS`, `BM25`, `pg_search`, `n-gram`이 각각 어떤 문제를 푸는지 이해하는 것이다.

| 질문 | 짧은 답 |
| --- | --- |
| `LIKE`와 FTS는 무엇이 다른가? | `LIKE`는 문자열 포함 여부를 보고, FTS는 문서를 토큰화해서 검색 가능한 구조로 만든다. |
| BM25는 왜 필요한가? | 단순히 많이 나온 단어가 아니라 드문 단어, 문서 길이, 등장 빈도를 함께 보며 관련도 점수를 만든다. |
| pg_search는 무엇인가? | PostgreSQL 테이블에 ParadeDB(BM25) 인덱스를 만들고 SQL로 검색과 score 정렬을 하게 해주는 확장이다. |
| 한글 검색에서 n-gram은 왜 자주 나오나? | `결제`와 `결제했다`처럼 정확히 같은 토큰이 아닌 표현을 글자 조각 기반으로 이어주기 위해 쓴다. |
| Elasticsearch를 대체할 수 있나? | 일부 서비스에서는 가능하지만, 대규모 분산 검색과 복잡한 analyzer 파이프라인은 여전히 별도 검색 엔진이 강하다. |

## 검색 문제를 먼저 나누기

검색을 하나의 기능으로 뭉뚱그리면 판단이 흐려진다. 실제로는 최소 네 가지 문제가 섞여 있다.

| 문제 | 예시 | 필요한 도구 |
| --- | --- | --- |
| 포함 여부 | `description`에 `카드`가 있는가 | `LIKE`, FTS, match query |
| 토큰화 | `카드 결제`를 어떤 단위로 나눌 것인가 | tokenizer |
| 랭킹 | 어떤 결과를 먼저 보여줄 것인가 | `ts_rank`, BM25 score |
| 언어 처리 | `결제`, `결제했다`, `결제금액`을 어떻게 다룰 것인가 | n-gram, 형태소 분석기, 정규화 |

가장 단순한 검색은 포함 여부만 본다.

```sql
SELECT *
FROM transactions
WHERE description LIKE '%카드 결제%';
```

이 쿼리는 이해하기 쉽지만 검색 기능으로는 한계가 분명하다.

```text
- 관련도 순서가 없다.
- 단어가 떨어져 있으면 놓칠 수 있다.
- 흔한 단어와 드문 단어의 중요도를 구분하지 않는다.
- 데이터가 커질수록 성능이 불리하다.
- 한국어 어미, 조사, 복합어 처리가 약하다.
```

그래서 검색을 제대로 만들 때는 보통 다음 흐름으로 간다.

```text
원문 문서
  ↓
토큰화
  ↓
정규화
  ↓
역색인 생성
  ↓
검색어도 같은 방식으로 분석
  ↓
매칭 문서 찾기
  ↓
관련도 점수 계산
  ↓
점수 높은 순서로 정렬
```

PostgreSQL 기본 FTS와 pg_search는 이 흐름을 PostgreSQL 안에서 해결하려는 선택지다.

## PostgreSQL 기본 FTS

PostgreSQL은 자체 Full Text Search 기능을 제공한다. 핵심 구성 요소는 이 정도만 먼저 알면 된다.

| 구성 요소 | 역할 |
| --- | --- |
| `to_tsvector()` | 문서를 검색 가능한 lexeme 목록으로 바꾼다. |
| `plainto_tsquery()` | 사용자가 입력한 일반 문장을 검색 query로 바꾼다. |
| `to_tsquery()` | AND, OR, FOLLOWED BY 같은 연산자를 직접 쓴 검색 query를 만든다. |
| `@@` | `tsvector`와 `tsquery`가 매칭되는지 검사한다. |
| `ts_rank()` / `ts_rank_cd()` | 검색 결과에 관련도 점수를 준다. |
| GIN index | FTS 검색을 빠르게 하기 위한 대표 인덱스다. |

예를 들어 거래 설명을 검색하고 싶다면 이렇게 시작할 수 있다.

```sql
CREATE INDEX trans_fts_idx
ON transactions
USING GIN (
    to_tsvector('simple', coalesce(description, ''))
);
```

`coalesce(description, '')`를 넣는 이유는 `description`이 `NULL`일 때 전체 `tsvector` 결과가 `NULL`이 되는 것을 피하기 위해서다.

검색 쿼리는 다음처럼 쓸 수 있다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    ts_rank(
        to_tsvector('simple', coalesce(description, '')),
        plainto_tsquery('simple', '카드 결제')
    ) AS rank
FROM transactions
WHERE to_tsvector('simple', coalesce(description, ''))
      @@ plainto_tsquery('simple', '카드 결제')
ORDER BY rank DESC
LIMIT 10;
```

이 쿼리는 `카드 결제`를 `tsquery`로 바꾸고, `description`을 `tsvector`로 바꾼 뒤, 매칭되는 row를 `rank` 높은 순서로 가져온다. 단순히 `WHERE`로 찾고 끝나는 것이 아니라 `ORDER BY rank DESC`까지 붙는다는 점이 중요하다.

PostgreSQL 기본 FTS는 내부 관리자 검색, 간단한 게시글 검색, 로그 검색에는 충분히 좋은 출발점이다. 다만 검색 품질을 제품 기능의 중심에 놓기 시작하면 한계도 보인다.

## 기본 FTS의 한계

첫 번째 한계는 랭킹 품질이다. PostgreSQL의 `ts_rank`와 `ts_rank_cd`도 관련도 점수를 제공하지만, 검색엔진에서 널리 쓰이는 BM25 랭킹과 같은 모델은 아니다. 공식 문서도 내장 ranking 함수가 예시 성격이며, 애플리케이션에 따라 추가 랭킹 요소를 결합할 수 있다고 설명한다.

검색에서 중요한 것은 단순히 많이 등장한 단어가 아니다. 예를 들어 거래 설명에 이런 단어가 있다고 하자.

```text
결제
카드
일등석
부동산
해외송금
```

`결제`는 거의 모든 거래 설명에 자주 나올 수 있다. 반면 `일등석`, `부동산`, `해외송금`은 상대적으로 드물다. 좋은 검색 랭킹은 이 차이를 반영해야 한다.

```text
흔한 단어: 점수를 덜 줌
드문 단어: 점수를 더 줌
```

두 번째 한계는 한국어 처리다. 문서에는 이런 값이 있다고 하자.

```text
편의점 카드 결제
```

사용자가 이렇게 검색한다.

```text
결제했다
```

토큰화 결과가 각각 `결제`, `결제했다`로 갈라지면 검색엔진 입장에서는 둘이 다른 토큰이다.

```text
결제 != 결제했다
```

한국어는 조사와 어미 변화가 많다.

```text
결제
결제했다
결제하면
결제는
결제도
결제금액
```

이 문제는 PostgreSQL 기본 FTS만으로 매끄럽게 해결하기 어렵다. 이때 BM25 기반 검색 확장과 tokenizer 전략을 같이 고민하게 된다.

## BM25를 어떻게 이해하면 좋을까

BM25는 검색 결과의 관련도 점수를 계산하는 대표적인 랭킹 알고리즘이다. 정확한 수식을 외울 필요는 없다. 실무 감각으로는 이렇게 이해하면 충분하다.

```text
BM25 점수 =
    검색어가 문서에 얼마나 잘 들어 있는가
  + 그 단어가 전체 문서에서 얼마나 희귀한가
  + 문서 길이에 비해 얼마나 집중적으로 등장하는가
```

핵심 요소는 세 가지다.

| 요소 | 의미 | 쉬운 예시 |
| --- | --- | --- |
| TF | 검색어가 현재 문서에 몇 번 등장하는가 | `결제`가 1번보다 3번 나온 문서가 더 관련 있을 수 있다. |
| TF 포화 | 많이 나온다고 점수가 무한정 커지지는 않음 | `결제` 50번과 51번의 차이는 거의 없다. |
| IDF | 전체 문서에서 드문 단어일수록 더 중요 | `결제`보다 `일등석`이 더 강한 신호일 수 있다. |
| 문서 길이 보정 | 짧은 문서에 검색어가 집중되면 더 강한 신호 | `카드 결제`라는 짧은 설명은 관련도가 높다. |

아주 단순화하면 이런 모양이다.

```text
score(D, Q) = Σ IDF(q) × TF 보정값 × 문서 길이 보정값
```

여기서 `D`는 문서, `Q`는 검색어, `q`는 검색어 안의 각 단어다.

주니어 개발자 입장에서는 이 문장만 기억해도 된다.

```text
BM25는 단어가 많이 나온다고 무조건 1등을 주지 않는다.
흔한 단어인지, 드문 단어인지, 문서 길이가 어떤지도 같이 본다.
```

## ParadeDB pg_search의 위치

`pg_search`는 ParadeDB가 제공하는 PostgreSQL 확장이다. 역할은 PostgreSQL 테이블에 BM25 인덱스를 만들고, SQL 안에서 검색과 score 정렬을 할 수 있게 하는 것이다.

기존에 Elasticsearch를 붙이면 대략 이런 구조가 된다.

```text
PostgreSQL
  ↓ 데이터 동기화
Elasticsearch / OpenSearch
  ↓
검색 API
```

pg_search를 쓰면 구조가 이렇게 바뀐다.

```text
PostgreSQL table
  ↓
PostgreSQL 내부 BM25 index
  ↓
SQL 검색 + score 정렬
```

장점은 분명하다.

| 항목 | 설명 |
| --- | --- |
| 동기화 단순화 | 별도 검색 서버로 데이터를 복제하는 파이프라인이 줄어든다. |
| SQL 결합 | 검색 결과에 PostgreSQL 필터, 정렬, JOIN을 같이 적용하기 쉽다. |
| BM25 랭킹 | 단순 포함 검색보다 검색엔진에 가까운 관련도 정렬을 할 수 있다. |
| 운영 부담 감소 | 검색 클러스터를 따로 운영하지 않아도 되는 경우가 생긴다. |

단점도 같이 봐야 한다.

| 항목 | 설명 |
| --- | --- |
| 확장 의존성 | PostgreSQL extension 설치와 버전 관리가 필요하다. 0.25.0부터는 pgvector도 필요하다. |
| 문법 변화 | ParadeDB는 `0.20.0`부터 새 SQL 문법으로 이동했다. 0.25.0부터 인덱스 접근 방법 이름은 `USING paradedb`이고, `USING bm25`는 하위 호환 alias다. |
| 분산 검색 한계 | Elasticsearch/OpenSearch처럼 검색 인덱스를 독립적으로 대규모 확장하는 구조는 아니다. |
| 인덱스 설계 비용 | 어떤 컬럼을 BM25 인덱스에 넣을지, 어떤 tokenizer를 쓸지 판단해야 한다. |

2026년 8월 26일 확인한 ParadeDB 문서는 pg_search v0.25.4 기준이다. 기본 검색 SQL은 여전히 `|||`, `&&&`, `###`, `pdb.score()`가 중심이다. `@@@`는 지금 query builder 함수용 연산자로 남아 있으므로, 기본 match 연산자와는 역할을 구분해서 보면 된다. 기존 글이나 예제에서 `paradedb.score()`, `paradedb.match()`를 봤다면 0.20.0 이전 함수 이름일 수 있으므로 버전 확인이 필요하다.

## 예제 테이블

금융 거래 검색을 예로 들면 테이블은 다음처럼 생겼다고 하자.

```sql
CREATE TABLE transactions (
    transaction_id BIGSERIAL PRIMARY KEY,
    account_id     BIGINT NOT NULL,
    customer_tier  VARCHAR(20) NOT NULL,
    description    TEXT NOT NULL,
    amount         NUMERIC(15,2) NOT NULL,
    branch_id      BIGINT,
    metadata       JSONB,
    created_at     TIMESTAMPTZ DEFAULT NOW()
);
```

검색 대상은 주로 `description`이다.

```text
강남 백화점 카드 결제
편의점 카드 결제
온라인 쇼핑몰 결제
해외 카드 결제 환전 수수료 포함
ATM 현금 출금
계좌 이체 송금 완료
급여 입금 처리
항공권 결제 일등석
```

검색 서비스 관점에서 `description` 하나하나는 검색 문서다. 문서가 짧기 때문에 부분 매칭, 어미 변화, 희귀 단어 가중치가 체감 품질에 크게 영향을 준다.

## BM25 인덱스 만들기

ParadeDB의 기본 검색 인덱스는 다음처럼 만든다. 0.25.0부터 공식 이름은 ParadeDB index이고 접근 방법은 `USING paradedb`다. 아래 SQL의 `USING bm25`는 같은 인덱스의 하위 호환 alias다.

```sql
CREATE INDEX trans_search_idx ON transactions
USING bm25 (transaction_id, description)
WITH (key_field='transaction_id');
```

의미는 단순하다.

```text
transactions 테이블에 BM25 검색 인덱스를 만든다.
transaction_id를 row 식별자로 사용한다.
description 컬럼을 검색 대상으로 사용한다.
```

여기서 `key_field`가 중요하다. BM25 인덱스가 검색 결과를 실제 테이블 row와 연결하려면 고유 식별자가 필요하다. 보통 primary key를 쓴다.

| 규칙 | 설명 |
| --- | --- |
| UNIQUE여야 함 | 보통 primary key를 사용한다. 공식 문서는 UNIQUE 제약을 요구한다. |
| 컬럼 목록 맨 앞 | key field는 인덱스 컬럼 목록의 첫 번째여야 한다. |
| 인덱스에 포함되어야 함 | `USING bm25 (transaction_id, description)`처럼 들어가야 한다. |
| score 계산에 사용됨 | `pdb.score(transaction_id)`처럼 key field를 넘긴다. |

좋은 예는 이렇다.

```sql
CREATE INDEX trans_search_idx ON transactions
USING bm25 (transaction_id, description)
WITH (key_field='transaction_id');
```

운영에서는 검색, 필터, 정렬에 자주 쓰는 컬럼도 함께 고려할 수 있다. ParadeDB 문서는 한 테이블에 ParadeDB 인덱스를 하나만 둘 수 있다고 설명하며, 검색 query에 등장할 수 있는 컬럼을 인덱스에 포함하는 방향을 권한다.

```sql
CREATE INDEX trans_search_idx ON transactions
USING bm25 (
    transaction_id,
    description,
    customer_tier,
    amount,
    created_at,
    metadata
)
WITH (key_field='transaction_id');
```

하지만 인덱스를 무작정 크게 만들면 안 된다.

```text
- INSERT/UPDATE 비용 증가
- 디스크 사용량 증가
- VACUUM/maintenance 부담 증가
- 인덱스 재생성 시간 증가
```

인덱스는 "나중에 쓸지도 모르는 모든 컬럼"이 아니라 실제 검색 화면과 API 요구사항을 기준으로 설계해야 한다.

## 현재 문법으로 검색하기

ParadeDB의 기본 match query는 검색어를 tokenizer로 나눈 뒤 매칭한다. 공식 문서는 match를 두 가지로 나눈다.

- Match Any: `|||`는 검색어 토큰 중 하나라도 포함하면 매칭한다.
- Match All: `&&&`는 검색어 토큰을 모두 포함해야 매칭한다.

순서와 인접성까지 맞아야 하면 phrase 연산자 `###`를 쓴다. 이 글에서는 세 연산자를 같이 비교한다.

`카드 결제`를 넓게 검색하려면 `|||`를 쓴다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description ||| '카드 결제'
ORDER BY score DESC
LIMIT 10;
```

이 쿼리는 `카드` 또는 `결제` 중 하나라도 포함한 결과를 찾는다. 따라서 `주차료 결제`, `카드론 이자 납부`처럼 일부 토큰만 맞는 결과도 들어올 수 있다.

사용자 의도가 "카드와 결제가 모두 들어간 거래"라면 `&&&`가 더 낫다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description &&& '카드 결제'
ORDER BY score DESC
LIMIT 10;
```

`카드 결제`라는 문구가 붙어 있는 결과를 더 엄격하게 찾고 싶다면 `###`를 쓴다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description ### '카드 결제'
ORDER BY score DESC
LIMIT 10;
```

검색 기능에서 가장 중요한 줄은 결국 이것이다.

```sql
ORDER BY score DESC
```

검색은 찾는 것으로 끝나지 않는다. 사용자는 검색어와 가장 관련 있는 결과가 먼저 나오길 기대한다. `ORDER BY transaction_id`나 `ORDER BY created_at`만 두면 검색 결과는 나오지만 검색 품질은 낮아진다.

실무에서는 score와 비즈니스 정렬을 함께 쓴다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    customer_tier,
    created_at,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description &&& '카드 결제'
ORDER BY score DESC, created_at DESC
LIMIT 10;
```

이 쿼리는 먼저 관련도 높은 결과를 보여주고, score가 같으면 최신 거래를 먼저 보여준다.

## 한글 검색과 n-gram

한글 검색에서 자주 부딪히는 문제는 사용자가 입력한 표현과 DB에 저장된 표현이 정확히 같은 토큰으로 떨어지지 않는다는 점이다.

```text
문서: 편의점 카드 결제
검색어: 결제했다
```

기본 tokenizer가 이 둘을 각각 `결제`, `결제했다`로 본다면 둘은 매칭되지 않을 수 있다. 이때 n-gram tokenizer를 쓰면 글자를 작은 조각으로 나눈다.

```text
결제했다
  ↓
2-gram: 결제, 제했, 했다
3-gram: 결제했, 제했다
```

그러면 `결제했다` 안에도 `결제` 조각이 생긴다. 문서 `카드 결제`에도 `결제` 조각이 있으므로 둘이 매칭될 가능성이 높아진다.

ParadeDB의 현재 문법에서는 n-gram tokenizer를 casting 형태로 붙일 수 있다.

```sql
DROP INDEX IF EXISTS trans_search_idx;

CREATE INDEX trans_search_idx ON transactions
USING bm25 (
    transaction_id,
    (description::pdb.ngram(2,3))
)
WITH (key_field='transaction_id');
```

토큰화를 직접 확인할 수도 있다.

```sql
SELECT '결제했다'::pdb.ngram(2,3)::text[];
```

개념적으로 기대하는 결과는 다음과 비슷하다.

```text
{결제, 제했, 했다, 결제했, 제했다}
```

n-gram 인덱스를 적용한 뒤에는 이런 검색이 가능해진다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description ||| '결제했다'
ORDER BY score DESC
LIMIT 10;
```

다만 n-gram은 형태소 분석이 아니다.

```text
결제했다는 "결제"의 활용형이다.
```

이렇게 문법적으로 이해하는 것이 아니라,

```text
결제했다 → 결제, 제했, 했다, 결제했, 제했다
```

처럼 조각을 만들어 겹치는 부분을 찾는 방식이다. 그래서 장점과 단점이 뚜렷하다.

| 구분 | 설명 |
| --- | --- |
| 장점 | 한글 부분 검색에 강하다. |
| 장점 | 상품명, 거래 설명, 짧은 텍스트에서 체감 품질이 좋다. |
| 장점 | 별도 형태소 분석기 없이 빠르게 적용할 수 있다. |
| 단점 | 인덱스 크기가 커질 수 있다. |
| 단점 | 너무 넓게 매칭되어 노이즈가 생길 수 있다. |
| 단점 | 의미를 이해하는 것은 아니다. |
| 단점 | n-gram 설정에 따라 phrase/proximity query 제약이 생길 수 있다. |

특히 ParadeDB 문서는 n-gram token이 서로 겹치기 때문에 기본적으로 token position을 저장하지 않는다고 설명한다. 그래서 phrase, phrase prefix, regex phrase, proximity query는 n-gram 필드에서 기본 지원되지 않는다. 예외는 `min_gram`과 `max_gram`을 같게 두고 `positions=true`를 켠 경우다. 이 부분은 버전과 쿼리 요구사항에 따라 테스트가 필요하다.

## 한국어 검색 전략 선택

한국어 검색은 하나의 정답이 없다. 검색 대상과 운영 여건에 따라 선택지가 달라진다.

| 방식 | 장점 | 단점 | 추천 상황 |
| --- | --- | --- | --- |
| PostgreSQL 기본 FTS | 내장 기능이라 운영이 단순하다. | 한글 품질과 랭킹 품질에 한계가 있다. | 관리자용 간단 검색 |
| pg_search + 기본 tokenizer | PostgreSQL 안에서 BM25 score를 쓸 수 있다. | 한국어 부분 매칭은 부족할 수 있다. | 게시글, 로그, 짧은 설명 검색의 첫 단계 |
| pg_search + n-gram | 부분 검색에 강하고 적용이 비교적 쉽다. | 인덱스 크기와 노이즈가 늘 수 있다. | 상품명, 거래 설명, 짧은 한글 텍스트 |
| 한국어 tokenizer | 형태소 기반 품질을 기대할 수 있다. | 사전, 버전, 운영 복잡도가 생긴다. | 검색 품질이 중요한 한국어 서비스 |
| Elasticsearch/OpenSearch | analyzer, synonym, autocomplete, 분산 검색이 강하다. | 운영과 동기화가 복잡하다. | 검색이 제품의 중심인 대규모 서비스 |
| 앱 레벨 정규화 | 도메인 규칙을 정확히 반영할 수 있다. | 직접 구현과 유지보수 부담이 있다. | 약어, 상품코드, 사내 용어가 많은 서비스 |

거래 설명처럼 짧은 텍스트에서는 `pg_search + n-gram`이 꽤 실용적인 출발점이 될 수 있다. ParadeDB 문서의 Lindera는 사전 기반 형태소 분석(한국어는 KoDic)이고, Chinese compatible는 CJK 글자 단위 토큰이다. 형태소 품질이 중요하면 Lindera를 검토하고, 이 글의 실습 경로는 짧은 거래 설명의 n-gram이다.

```text
카드 결제
결제했다
결제금액
카드결제
```

이런 검색어가 자주 들어온다면 n-gram이 사용자의 기대에 가까운 결과를 만들어줄 가능성이 높다. 반대로 긴 문서 본문 전체에 `ngram(2,3)`을 무턱대고 걸면 인덱스가 커지고 노이즈가 늘 수 있다.

## Elasticsearch와 비교하기

pg_search의 매력은 PostgreSQL 안에서 검색 품질을 올릴 수 있다는 점이다. 하지만 이것이 언제나 Elasticsearch/OpenSearch를 대체한다는 뜻은 아니다.

| 항목 | Elasticsearch/OpenSearch | PostgreSQL + pg_search |
| --- | --- | --- |
| 구조 | 별도 검색 서버 | PostgreSQL 내부 확장 |
| 데이터 저장 | DB와 검색 인덱스가 분리될 수 있음 | PostgreSQL 중심 |
| 동기화 | 별도 파이프라인 필요 | 상대적으로 단순 |
| 불일치 위험 | 있음 | 낮음 |
| 랭킹 | BM25와 다양한 ranking pipeline | BM25 기반 score |
| analyzer | 매우 풍부 | PostgreSQL extension/tokenizer 범위 |
| 분산 확장 | 강함 | PostgreSQL 스케일에 묶임 |
| SQL 결합 | 보통 denormalization 필요 | JOIN/필터와 결합하기 쉬움 |
| 운영 난이도 | 높음 | 상대적으로 낮음 |

판단 기준은 이렇게 잡으면 된다.

PostgreSQL 기본 FTS만으로도 충분한 경우:

```text
- 검색 규모가 작다.
- 관리자 페이지 검색이다.
- 검색 품질보다 구현 단순성이 중요하다.
- 한글 부분 검색 요구가 강하지 않다.
```

pg_search가 좋은 경우:

```text
- PostgreSQL 하나로 운영하고 싶다.
- Elasticsearch 동기화 구조가 부담스럽다.
- BM25 관련도 정렬이 필요하다.
- SQL 필터와 검색을 같이 쓰고 싶다.
- 검색 대상이 게시글, 거래 설명, 상품명, 로그처럼 테이블 중심이다.
```

Elasticsearch/OpenSearch가 좋은 경우:

```text
- 검색 트래픽이 매우 크다.
- 검색 인덱스를 독립적으로 확장해야 한다.
- autocomplete, synonym, 복잡한 analyzer가 중요하다.
- 여러 데이터 소스를 통합 검색해야 한다.
- 검색팀이나 운영팀이 있고 클러스터 운영이 가능하다.
```

## Spring Boot에서 붙이면 어떤 구조인가

Spring Boot에서 쓴다고 해서 구조가 복잡해지는 것은 아니다. 핵심은 SQL을 안전하게 감싸는 것이다.

```text
Controller
  ↓
Service
  ↓
Repository / DAO
  ↓
PostgreSQL SQL
  ↓
BM25 index
```

검색 API는 이런 모양이 된다.

```text
GET /api/transactions/search?q=카드%20결제
```

Repository SQL은 다음과 비슷하다.

```sql
SELECT
    transaction_id,
    description,
    amount,
    customer_tier,
    created_at,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description &&& :keyword
ORDER BY score DESC, created_at DESC
LIMIT :limit OFFSET :offset;
```

주의할 점은 검색어를 SQL 문자열에 직접 붙이지 않는 것이다.

나쁜 예:

```java
String sql = "WHERE description &&& '" + keyword + "'";
```

좋은 예:

```java
String sql = "WHERE description &&& :keyword";
```

검색 문법이 특수 연산자를 쓰더라도 사용자 입력은 반드시 바인딩 파라미터로 넘겨야 한다.

## 운영 체크리스트

검색은 인덱스를 만들었다고 끝나지 않는다. 운영에서는 최소한 다음을 확인해야 한다. 2026-08-26 기준 pg_search 0.25.0부터는 pgvector의 `vector` 타입에 의존하므로, 설치 문서는 `CREATE EXTENSION pg_search CASCADE`를 기준으로 한다.

### 인덱스를 실제로 타는가

```sql
EXPLAIN ANALYZE
SELECT
    transaction_id,
    description,
    pdb.score(transaction_id) AS score
FROM transactions
WHERE description &&& '카드 결제'
ORDER BY score DESC
LIMIT 10;
```

확인할 것:

```text
- Seq Scan이 뜨는지
- BM25 인덱스가 사용되는지
- LIMIT이 적용되는지
- score 정렬 비용이 과도하지 않은지
```

### 인덱스 생성 시간을 볼 수 있는가

큰 테이블에서 `CREATE INDEX`는 오래 걸릴 수 있다. PostgreSQL의 `pg_stat_progress_create_index`를 별도 connection에서 확인하면 진행률을 대략 볼 수 있다.

```sql
SELECT pid, phase, blocks_done, blocks_total
FROM pg_stat_progress_create_index;
```

### n-gram 인덱스 크기를 감당할 수 있는가

n-gram은 토큰 수를 늘린다. 다음 요소에 따라 인덱스 크기가 커진다.

```text
- 텍스트 길이
- min_gram / max_gram 범위
- row 수
- indexed column 개수
```

짧은 거래 설명에는 괜찮을 수 있지만, 긴 본문 전체에 넓은 n-gram 범위를 적용하면 부담이 커질 수 있다.

### VACUUM과 업데이트 패턴을 알고 있는가

PostgreSQL은 UPDATE/DELETE 후 dead row가 생긴다. 검색 인덱스도 테이블 변경 패턴의 영향을 받으므로 autovacuum 상태, bulk update, reindex 필요성을 같이 봐야 한다.

```sql
VACUUM transactions;
```

운영에서는 수동 `VACUUM`을 반복하는 것이 아니라 테이블 변경량과 autovacuum 설정을 함께 봐야 한다.

## 주니어 개발자가 꼭 가져가야 할 문장

첫째, `LIKE` 검색은 문자열 포함 여부를 보는 것이고 FTS는 문장을 토큰화해서 검색 가능한 구조로 만드는 것이다.

둘째, 검색 기능은 찾는 것에서 끝나지 않고 관련도 높은 순서로 정렬하는 것까지 포함한다.

셋째, BM25는 검색어 빈도, 단어 희소성, 문서 길이를 함께 고려해서 관련도 점수를 계산한다.

넷째, Elasticsearch는 강력하지만 PostgreSQL과 동기화 파이프라인이 생길 수 있다.

다섯째, pg_search는 PostgreSQL 안에서 BM25 기반 검색을 수행해 구조를 단순하게 만들 수 있다.

여섯째, 한글 검색에서는 `결제`와 `결제했다`가 다르게 처리될 수 있으므로 n-gram이나 한국어 tokenizer를 검토해야 한다.

## 내 결론

PostgreSQL 기본 FTS는 검색의 출발점으로 좋다. `to_tsvector`, `plainto_tsquery`, `@@`, `ts_rank`, GIN 인덱스를 이해하면 검색이 단순 문자열 조건이 아니라 토큰화와 랭킹 문제라는 감각을 잡을 수 있다.

하지만 검색 품질을 더 끌어올리고 싶다면 BM25를 봐야 한다. ParadeDB `pg_search`는 PostgreSQL 안에서 BM25 인덱스와 score 정렬을 제공하므로, 별도 Elasticsearch 동기화 없이도 꽤 많은 검색 요구를 처리할 수 있다. 특히 게시글, 거래 설명, 상품명, 로그처럼 PostgreSQL 테이블 중심의 검색에는 좋은 선택지가 된다.

한글 검색에서는 n-gram을 신중하게 쓰면 실용적인 개선이 가능하다. `결제했다`로 `카드 결제`를 찾고 싶은 요구는 실제 서비스에서 자주 나온다. 다만 n-gram은 의미 분석이 아니라 글자 조각 매칭이다. 인덱스 크기, 노이즈, phrase query 제약을 반드시 테스트해야 한다.

내가 실제로 도입한다면 순서는 이렇게 잡겠다.

1. PostgreSQL 기본 FTS로 검색 요구와 데이터 분포를 먼저 확인한다.
2. 관련도 정렬이 부족하면 pg_search BM25 인덱스를 작은 범위에 적용한다.
3. `|||`, `&&&`, `###`의 결과 차이를 실제 사용자 검색어로 비교한다.
4. 한글 부분 검색이 중요하면 `pdb.ngram(2,3)`을 실험한다.
5. `EXPLAIN ANALYZE`, 인덱스 크기, insert/update 비용, 검색 로그를 보고 확장 여부를 결정한다.

정리하면 이렇다. PostgreSQL 안에서 검색엔진을 만들 수는 있다. 다만 좋은 검색은 인덱스 하나로 끝나지 않는다. 토큰화, 랭킹, 언어 처리, 운영 비용을 같이 설계해야 한다.
